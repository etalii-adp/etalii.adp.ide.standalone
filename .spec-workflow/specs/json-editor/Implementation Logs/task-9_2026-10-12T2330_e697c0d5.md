# Implementation Log: Task 9

**Summary:** The service's schema requests go through resolveSchemaReference, deciding the raw reference before any URL arithmetic, and are answered from the SchemaFiles map or refused with the reason; $ref follows the same rules. Every json-schema.org dialect the service carries (draft-04, draft-07, 2019-09, 2020-12) applies to a document that is itself a schema; any other dialect is refused as one ADP cannot check against. Schema breaks are errors, a deprecated property a warning; the not-allowed finding on the root $schema property is dropped by its range, not its sentence. An unresolvable reference, a schema that is not valid JSON and an unsupported dialect each become one information finding on the $schema property, with the reason. The status line gives the schema's title, else its reference, "No schema", "Reading <ref>", "<ref> <reason>", "Too large to check" above 1,000,000 characters, or "Schema support stopped" after a throw, which is caught once, after which findings come from the Lezer grammar. A self-referencing schema is held by a test with a time limit. Panel tests: a schema arriving after the document makes findings appear, and a new revision changes them without reopening (5.8); a failed schema file is reported once on the $schema line. Measured on the Performance section's 5,000-line document against a 2,000-line schema: findings 13.7, 17.4 and 14.7 ms over three runs, against the bound of one second. Sabotage: the $schema filter, the size bound, the throw catch, URL arithmetic on refs, every carried dialect, unusable schemas ignored, the title ignored, the revision dropped, needs ignored and status not wired each turned their tests red. Removing the waiting state alone stayed green, because the service-level waiting path gives the same result: that is defence in depth, recorded rather than tested twice.
