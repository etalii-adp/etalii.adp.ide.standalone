# Implementation Log: Task 1

**Summary:** The binding resolver (Requirements 2.5, 3.1). Field paths, templates, collection bindings with `each`, and `when` conditions, resolving against a BindingSource of the element plus the module payload. Pure, no React, no DOM - resolution is a function of a binding and a source, which is what lets a guard, a test and a serialiser all handle the same value.

THE PROHIBITION IS IN THE TYPE, WHICH IS WHAT THE TASK ASKED FOR. Every field is a string, a number, a literal union or another Binding, so a function is assignable to none of them: `{ path: () => x }` does not compile. That is stronger than a comment, because it does not depend on anyone remembering it at the moment they are tired and the deadline is close.

BUT A TYPE CAN BE DEFEATED BY A CAST, so it is not the only mechanism, and I would not want the log to claim otherwise. A test pins what happens when someone casts past it: a function reached through a smuggled binding RESOLVES TO NOTHING rather than being invoked, and a second test proves the walker never invokes a function it passes through on the way to a field. So the escape hatch does not reopen through a cast either - it is inert rather than merely discouraged. Task 15's guard reads source text, which is the third mechanism and the only one that can see a cast at all. Three mechanisms, one claim, and each covers what the others cannot.

TWO RULES CHOSEN DELIBERATELY AND WRITTEN INTO THE CODE. (1) A path that does not resolve draws nothing rather than throwing, and every kind of failure - missing root, missing step, a step through a primitive - answers identically ON PURPOSE. A resolver that distinguished them would invite a caller to branch on why a field was absent, which is module logic arriving through the back door. A binding is authored data that ships to users; a declaration with a typo must leave a gap in one diagram rather than take the canvas down. (2) Inside an `each`, paths are rooted at the ITEM rather than the element, which is what lets an rdf row say `{predicate}` instead of `{payload.rows.0.predicate}`. That is the load-bearing case: a fixed set of named slots would serve c4 and leave the rdf family exactly where it is, and the renderers that hand-roll a LOOP are why this binds to a collection at all.

ONE LIMIT STATED RATHER THAN ENGINEERED AROUND. Literal text between two optional values survives when only one resolves, so `"{a} - {b}"` with no `b` reads `"a -"`. The remedy is a `when`, or two labels rather than one template. Punctuation-aware trimming would be a formatter guessing at intent, and I would rather the limit be a decision on the record than a surprise - so a test pins the current behaviour and a later "improvement" has to argue with it.

BindingSource keeps the payload SEPARATE from the element rather than merging them: the element is the library's contract, the payload is the module's, and a merge would let a module field shadow `x` - a collision surfacing as a drawing subtly wrong rather than as an error. `DiagramModelElement` gains no payload field here: task 6 decides what crosses the wire and this must not pre-empt it, which is also why the task's file list is exactly two files and I kept it that way.

TWO SABOTAGES, EACH SEEN TO FAIL FOR ITS OWN REASON. Rooting `each` at the element instead of the item reddens five collection facts including the load-bearing one. Invoking a function met while walking a path reddens exactly one test - the prohibition - which is the discrimination that makes it a guard rather than a smoke test.
