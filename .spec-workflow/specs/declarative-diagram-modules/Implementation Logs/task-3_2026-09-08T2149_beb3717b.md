# Implementation Log: Task 3

**Summary:** `decorations` - the closed glyph set the five component-less renderers need (Requirement 3.2). Twelve of the twenty-eight custom shapes wrap one shared component, about ten wrap one and add raw <text> which task 2 covers, and FIVE use no component whatsoever. Those five draw four things between them, and each is a test written the way its module writes it today: ansible's and helm's stub, causal-loop's badge, sparql's annotation, wardley's target.

CLOSED ON PURPOSE - line, path, circle, rect, marker, and no more. A decoration vocabulary that could express anything would be a renderer with extra steps, which is the thing this specification exists to remove.

DRAWN AND NOTHING ELSE: no hit-testing, no gesture, no anchor. That line keeps this a small closed set rather than a second element system growing beside the first, and it is asserted rather than asserted ABOUT - the canvas test reads pointerEvents and aria-hidden off the rendered group, and removing them reddens it.

THE ONE JUDGEMENT WORTH CHALLENGING, flagged at the point of use rather than buried. causal-loop's polarity arc is computed today by loopMarkerPath(x, y, r, clockwise) inside the renderer. As a declaration it arrives as a bound `d` - a path string the module's model produces - which keeps it DATA: checkable, serialisable, unable to call anything. That is the distinction the whole specification rests on, so a bound `d` is admissible where a function is not. But whether that arc is better as a bound `d` or as a named marker in the library's own registry is a real question and it belongs to the sufficiency table, not to me here. The doc-comment says so where an author will meet it.

A GUARD THIS TREE ALREADY HAD CAUGHT A REAL DEFECT OF MINE. noUnstyledLibraryClasses failed on library-decoration-text: the class had no rule anywhere, so the browser would have painted every decoration's text BLACK - no exception, no type error, nothing visible until someone opened the app. That guard exists because thirty-one of thirty-two library classes once had no CSS and a connect drag swept a solid black wedge across the diagram. I resolved it the way the guard's own contract offers, an exemption WITH A REASON, because library-decoration-text is the same category as library-element-label sitting directly beside it in that list: text carrying no fill of its own, coloured by the declaration's typography inline or by the module's className on the group, which is where a notation's colour belongs.

Numeric resolution added to the binding, because geometry binds to numbers and a declaration spelling those as text would be worse to read and worse to check. Parsing rather than a second numeric binding form - two resolvers can disagree about what payload.r means. A value that is not a number falls back rather than vanishing: a decoration that disappeared on a typo would be indistinguishable from one nobody declared.

Sabotages: making `to` absolute rather than relative to `from` reddens the stub; removing pointerEvents:none reddens the no-gesture rule. Each hits only its own claim. All 1114 pre-existing client tests pass unchanged. Worktree commit 7b2caa3b on claude/ddm.
