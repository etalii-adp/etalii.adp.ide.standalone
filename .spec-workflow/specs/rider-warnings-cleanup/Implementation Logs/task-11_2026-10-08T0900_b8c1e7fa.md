# Implementation Log: Task 11

**Summary:** There is no race in `DiagramDocumentReloadBridge`. The three accesses outside `_watcherLock` are single operations on `ConcurrentDictionary`, each atomic without the lock. The lock serializes only the compound steps on a watcher. The reason is stated at the fields, and each of the three lines carries a same-line suppression that gives it (`44b5bb01`). Looking for this race found a real one next to it, in `HierarchyService`. After the dispose, a late presence poll could start a recovery that read the token of a disposed `CancellationTokenSource`. Peter ruled "Read token early" on a decision card in the project thread on 2026-10-08. The fix landed with a guard that failed four runs out of four before the fix (`823a1180`).

## The verdict for `DiagramDocumentReloadBridge`

The inspection reported three accesses (`DiagramDocumentReloadBridge.cs:58, 61, 69`):
- `_documents[bodyPath] = ...` in `Track`
- `_registrations[registrationPath] = ...` in `Track`
- the fast-path `_watchers.ContainsKey(rootPath)` in `EnsureWatching`

The reasoning:
- All three fields are `ConcurrentDictionary`. A single read or write of one is atomic without a lock.
- `_watcherLock` serializes only the compound steps on a watcher: check, create, replace in `OnWatcherError`, and dispose. That is why two Opens never build two `FileSystemWatcher`s for one root. Nothing reads `_documents` or `_registrations` inside the lock at all.
- The inspector most likely ties these fields to the lock through the watcher callbacks. `CreateWatcher` runs only inside the lock and hands over `OnChange` and `OnWatcherError`, but those run on the watcher's thread.
- The unlocked `ContainsKey` is decided again under the lock on a miss. A hit is ordered before any concurrent replace or dispose, exactly as a locked read would be. A later failed re-creation in `OnWatcherError` ends in the same state as if `Track` had run entirely before it.
- `OnWatcherError` also enumerates `_documents` outside the lock. `ConcurrentDictionary.Values` is a snapshot, so that read cannot be torn.

What changed (`44b5bb01`, 8 lines added, no code changed):
- A comment at the field declarations says what the lock serializes and why the maps need no lock.
- Each of the three lines has `// ReSharper disable once InconsistentlySynchronizedField - Reason: ...`. The two writes read "one atomic ConcurrentDictionary write; _watcherLock serializes creating and disposing watchers, not the tracked set". The read reads "an atomic ConcurrentDictionary read as a fast path; a miss is decided again under _watcherLock below, and a hit orders before any concurrent replace or dispose exactly as a locked read would".

The lock was not widened. There was nothing to fix, so no concurrency test was written for the bridge.

`InconsistentlySynchronizedField`: 3 before (PR 4's run). 0 in the combined report-mode run (`/tmp/rw/pr5-inspect1.log`) and 0 in the first refusing run (`/tmp/rw/pr5-inspect-final.log`).

## The race found alongside it: `HierarchyService`

**The defect.** In `RunWatchAsync`, `recoveryCts` is a `using var`. The `finally` calls `await recoveryCts.CancelAsync()`, then `_hierarchyModelStore.Remove(watchId)`, and then the `using` disposes the source. `CancelAsync` asks for cancellation; it does not wait for `WatchRootPresenceAsync` to leave its loop. So the race runs like this:
1. The poll's delay has already completed, and it sits between `!Directory.Exists(rootPath)` and `onRootLost(...)` when the watch closes.
2. It calls `HandleRootLost` after the dispose.
3. If this is the first detection of the outage, `HandleRootLost` starts `_ = RecoverAsync()`, which reads `recoveryCts.Token`.
4. On a disposed source that throws `ObjectDisposedException`. The task nobody awaits faults, and the exception goes unobserved.

The existing `AccessToDisposedClosure` suppression said both callers "are shut down in the finally ... before the using disposes recoveryCts". That reason was false. A scratch program on SDK 10.0.112 (`/tmp/rw/e/ctsprobe/Program.cs`) confirmed both halves of the fix's premise. A token read before the dispose is cancelled, and a `Task.Delay` on it ends in `TaskCanceledException`. Reading `.Token` on the disposed source inside an async method throws `ObjectDisposedException` and faults the task.

**The ruling.** Read token early (option 1 of four: read the token early, do not dispose the source, leave it and correct the suppression's reason, other).

**The fix** (`823a1180`, `src/backend/EtAlii.Adp.Hierarchy/HierarchyService.cs`):
- `var recoveryToken = recoveryCts.Token;` is read once, beside the `using`, with a comment saying why. The presence poll and `RecoverAsync` both take that token. The `finally` always cancels before the dispose, so a late recovery gets a token that is already cancelled, and `WaitForRootRecoveryAsync` catches the cancellation at its first wait.
- The `AccessToDisposedClosure` suppression is removed, with its false reason.
- A guard-only seam, `internal Func<Task>? RootFoundMissing`, documented "Settable for guards only; production never sets it". The poll awaits it between finding the root gone and announcing it. `WatchRootPresenceAsync` became an instance method so it can read the seam. The seam is an instance property so parallel tests cannot share it.
- The first refusing inspector run reported the seam as `PropertyCanBeMadeInitOnly.Global`. The guard sets it in an object initializer and nothing sets it afterwards, so it is now `init` (`0981f54e`).

**The guard.** `src/backend/EtAlii.Adp.Hierarchy.Tests/HierarchyService.LateRecovery.Tests.cs`, `RootFoundMissingAsTheWatchCloses_StartsARecoveryThatDoesNotFaultOnTheDisposedSource`:
1. It runs a real watch on a temporary project and deletes the root.
2. The hook holds the poll at the seam.
3. The test cancels the watch and awaits `RunWatchAsync`, so the `finally` and the dispose have run.
4. It releases the poll and waits for the model's `HierarchyRootUnavailable`, which proves the late announcement ran.
5. It forces GC and finalizers, and asserts that `TaskScheduler.UnobservedTaskException` reported no exception from `HierarchyService`.

If the watch ends before the poll reaches the seam, the test reports the watch's own exception instead of timing out.
