# Tasks Document

One worktree for the whole spec: `.claude/worktrees/bars` — deliberately short, because the Windows MAX_PATH failure mode (apphost never produced, `dotnet test` reporting zero tests) is traced to long worktree names. Set `MSBUILDDISABLENODEREUSE=1` and `DOTNET_CLI_USE_MSBUILD_SERVER=0` before gating: concurrent MSBuild nodes have been diagnosed as the cause of 0xC0000005 host crashes on this machine. Capture every gate's exit code **into a variable before any pipe** — in a pipeline `$?` is the last command's status, so `dotnet test … | tail` reports `tail`'s success and a crashed or zero-test run reads as green.

This is a four-canvas change with no backend and no protocol work. Each canvas is one task, and the order is deliberate: **c4 first**, because it is the plainest content-bounds case and its call site becomes the pattern the next two copy; **wardley-map last of the wiring**, because it is the only one whose extent is not content bounds and doing it after three plain cases makes the difference obvious rather than formative.

**Two rules that apply to every wiring task below, stated once here.**

- **The shared component is expected to need no change** (Requirement 6.2). If a canvas cannot be wired without adding a prop, widening a type or altering behaviour in `src/client/src/canvas/scroll/`, that is a **stop-and-report**, not a thing to work around: raise it, and take one of the only two permitted outcomes — the component grows **once, centrally**, in a change that serves every consumer and leaves the existing five working (Requirement 6.4), or that canvas is **documented in `src/client/src/canvas/scroll/readme.md` as unable to use it, with the specific reason** (Requirement 6.3). Building a private scrollbar for that canvas is forbidden, and so is silently leaving it without one.
- **The three tests are named for the defect each catches** (Requirement 2.6). "Asserts the scrollbars work" is exactly the phrasing that requirement exists to prevent, because a test asserting the component is imported or rendered passes on a canvas whose thumb is inert.

- [ ] 1. c4 gains scrollbars — the pattern the next two follow
  - Files: `src/diagrams/c4/client/C4Canvas.tsx`, `src/diagrams/c4/client/C4Canvas.test.tsx`
  - Add a pure `scrollAxesOf(view, bounds)` beside the component returning `{ horizontal, vertical }`: `viewStart` from `view.x`/`view.y`, `viewSpan` from `view.w`/`view.h`, extent from `scrollExtentOf` over the drawn content's bounds with a proportional margin and a minimum span of one box width. Render `<CanvasScrollbars {...scrollAxesOf(view, bounds)} className="c4-scrollbars" onPan={(x, y) => setView(current => ({ ...current, x, y }))} />` as a sibling of the `<svg>` inside the canvas's wrapper. **`onPan` sets only `x` and `y`** — a thumb pans and never zooms, so `w`/`h` carry through untouched.
  - **No DOM measurement is needed and none SHALL be added**: `viewSpan` is `view.w`, not a pixel width divided by a scale. The pixels-per-unit consumer measures its element because it must; a `ViewBox` canvas that copies that has copied a workaround for a problem it does not have.
  - Three tests, each named for its defect: **a drag of the thumb pans the view** (catches an unwired `onPan`) — assert the rendered `viewBox` x moved in the drag's direction, and the same vertically; **a pan by other means moves the thumb** (catches the bars reading a stale or private copy of the view) — pan via the existing empty-canvas drag and assert the thumb's offset changed; **zoom changes the thumb's size, not merely its offset** (catches a hard-coded `viewSpan`) — wheel-zoom and assert the size fraction changed.
  - Drive the tests with **mouse events**, not pointer events: jsdom cannot dispatch pointer events meaningfully and `setPointerCapture` is not implemented there, which cost a debugging cycle on a sibling canvas.

  - Files: `src/diagrams/wardley-map/client/WardleyCanvas.tsx`, `src/diagrams/wardley-map/client/WardleyCanvas.test.tsx`
  - Same component, same call shape, **different extent source**: the map's own fixed coordinate space rather than content bounds, which its existing `fullView` constant already expresses (Requirement 3.3).   - The map's axes and their labels occupy the canvas edges, so the bars are inset with the component's existing `className` prop (Requirement 4.2) — the mechanism that already exists for a canvas with a ruler.
