# Tasks Document

One Developer owns this specification, per CLAUDE.md's one-owner-per-specification rule, and works it in one worktree (`.claude/worktrees/adop`, branch `features/azure-devops-pipeline-disl-fbl`). **The order is the design's ten steps and it is load-bearing**: the three module defects are repaired before the transcript is frozen (tasks 1 and 2), so the transcript never holds a wrong file; derivation is switched before reading (tasks 6 and 7, then task 8), and reading before writing (tasks 9 and 10), so that a difference in the transcript can be attributed to one change. Two of the design's steps are too large for one pull request and are two tasks each: step 4 is the library work (task 4) and the bundling (task 5), and step 8 is the planner (task 9) and the commands with the undo (task 10).

**Every task is one pull request into `develop` and leaves the four gates green.** A task whose transcript differs in a way this document does not name is not delivered. The only named differences are the edit hunks and the sentence of a refused undo, both at task 10.

**Task 3 is done in etalii-adp/etalii.adp**, through that repository's own pull request and checks. Task 12 returns there once, for the companion and the report of the gaps.

**What waits, and on what.** Nobody starts these early.

- **Task 4 waits on the definition of task 3 being written**, because it starts by loading that definition and listing what the loader refuses. **Task 5 waits on the pull request of task 3 being merged in etalii.adp**, because `bundle-disl.sh` bundles from that repository's `develop`.
- **Task 4 shares library work with `causal-loop-disl-fbl`**: `diagram.cycles` (that specification's L1), `drop.targets` in `ToolboxDerivation` (its L4) and what `forEach` over the cycles needs (its L3). Whichever specification reaches its library task first delivers them and the other rebases and uses them. Before starting task 4, read `develop` and the open pull requests for each of the three, and add none twice. `reachable` and `inCycle` are this specification's own. **Task 7 cannot be delivered before `diagram.cycles` is on `develop`**, whoever delivers it.
- **Requirement 8.2 waits on Q2 ruling a declared reader.** Under the default of Q2, which this document is written against, a plugin receives the move and nothing is built in `EditPlanner`. Task 4 claims the criterion, records that its condition does not hold, and builds it only if the ruling changes.
- **Task 11 depends on task 5 only** and may be worked in any place after it. It is still the same Developer's.
- **Five things wait on a language change in etalii-adp/etalii.adp and have no task here**: a declared reader for the file with a plugin for templates only (language gaps 1 to 8), an entry for this tool in the real-file corpus (the declared reader), findings B14 and B15 and `std.duplicateId` (each a small change of its own after this conversion, Q3), and `PipelineLayout` leaving (gap 10). Task 12 records each beside what it waits on.

**The amendments the design proposes.** This document is written against the recommended option of each amendment the design proposes; a ruling that differs is a small amendment to the tasks named.

- Amendment 1, the finding codes stated as `code` on each rule and built-in, with `x-azure-pipeline` mapping tools, actions and properties: tasks 3 and 7, and task 4 if `WireIdMap` is to gain a `findings` map instead.
- Amendment 2, the host's history keeps the stack and the undo command carries the library's inverse splice and digest: task 10.
- Amendment 3, a fixture for each finding a document can show, the others held by `BundledDefinition.Tests` and the companion: task 2, with task 5 (findings A1 to A4) and task 12 (findings A10 and A11).
