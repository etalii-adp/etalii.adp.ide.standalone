WHAT WAS MEASURED, AND HOW. All ten module document stores' `Reload` bodies were READ, not sampled - the seven that were previously inferred from three corroborating absences are now read individually. The figure the design states holds: TWO OF TEN stores keep the last good document on a failed reload by design (c4, causal-loop), with a branch that logs naming the path and returns without installing. The other eight are `TryRemove` then `GetOrLoad`, with no such branch.

BUT THE TEN SPLIT FOUR WAYS ON A PRESENT-BUT-UNREADABLE READ, NOT TWO. This is the correction:

| Behaviour on a present-but-unreadable body | Count | Stores |
| --- | --- | --- |
| Keeps last good by design, logs naming the path - R2.4's stated form | 2 | c4, causal-loop |
| Installs an EMPTY document | 6 | azure-pipeline, databricks, dependency-graph, rdf, timeline, wardley-map |
| THROWS out of `Reload` | 1 | mindmap |
| Reports it as a NAMED STATE on the entry - R2.2 permits this and names sparql | 1 | sparql |

THE DISTINCTION THAT MATTERS, and the one the design's current wording blurs: a MISSING file and a PRESENT-BUT-UNREADABLE file are different paths. They coincide for the six and diverge sharply for mindmap. `design.md` currently says `BodyDeleted`'s default "is correct only while a store installs an empty document on a failed read, which is what the other eight do today". Precisely: six install empty, mindmap throws, sparql names a state - so it is six, not eight, on the unreadable path. The CONCLUSION is unaffected, because the default's correctness turns on the MISSING-file path, and there all eight end up empty or naming the absence and never keep the last document. So the R2.4/R2.5 coupling binds for every one of them and the ruling that they land together per store is untouched. What was loose is the rationale, and the corrected version is better because it isolates which path decides it.

MINDMAP'S MECHANISM, because it is the shape that defeats a converter. `MindmapDocumentStore.Load` has NO `IOException` catch - zero, verified rather than skimmed. So a present-but-unreadable body throws out of `Load`, the assignment `_documents[bodyPath] = Load(bodyPath)` never happens, and the cache therefore keeps the last good document. The throw is then swallowed two layers up by `RootFolderWatcher.Dispatch`, whose catch-all logs "Applying a {ChangeType} watcher event for {Path} failed; the change is lost until the next reconcile". So mindmap SATISFIES R2.4's OUTCOME BY EXCEPTION AND A CATCH-ALL, AND FAILS ITS STATED FORM: no warning naming the path comes from the store. A converter working from "eight install empty" would write the conversion against a behaviour mindmap does not have.

IT CANNOT KILL THE PROCESS, checked rather than assumed either way. The ordinary reload path at `DiagramDocumentReloadBridge.cs:183` (`ReloadIfTracked`) is NOT wrapped - only the overflow-recovery path guards per document - but `RootFolderWatcher.Dispatch` catches `Exception` around every `onChange` invocation, so nothing reaches a watcher callback unguarded.

THE WRITABLE COUNT IS NINE, NOT TEN, by four independent methods that agree and a total that reconciles: a public `Save` on the store (9), the modules whose production code calls a store `Save` (the same 9, by name), a `_selfWrites` set (9 of 10), and sparql's own comment - "No self-write guard, unlike every sibling store: this store never writes". The reconciliation is what closes it: 9 writable document stores + 1 read-only document store (sparql) + 3 read-only analysis stores that are folder- or solution-keyed with no save at all (`AnsibleProjectStore`, `DependencyGraphStore`, `HelmChartStore`) = the design's own independently-stated 13 implemented modules. Task 6's "ten writable stores" counts sparql twice, once in the ten and again as task 7's read-only store; that correction is held because `tasks.md` is under pending card `approval_1790275851689_hnszrsxls`.

WHAT THIS MEANS FOR TASK 5'S SHAPE, stated as an open question rather than settled in passing. The four behaviours are NOT four candidates for one decision - the requirements already distinguish three situations, and reading them that way collapses most of the choice. R2.2 governs a FIRST load whose file cannot be read: open empty and warn naming the path, unless the module declares unreadable-as-a-reported-state, which causal-loop and sparql do. R2.4 governs a RELOAD of a present-but-unreadable file: keep the last good document and warn. R2.5 and R2.6 govern a MISSING body confirmed through `BodyDeleted`: become the empty document. So the split measures how far each store sits from rules that already exist, rather than offering the lifecycle a free choice.

THE ONE GENUINELY OPEN POINT: R2.2 carries an "unless the module declares" escape and R2.4 carries none. causal-loop does BOTH - it declares (its entry has an `Error`) and it keeps last good on reload - which shows the two are compatible. sparql declares and does NOT keep last good: its `Load` returns an entry carrying an error message, so a reload of a momentarily-unreadable query replaces a good one. Whether a declaring module keeps last good on RELOAD, or installs its named state, is the question put to the Scrum master before any code is cut. It decides what every conversion does with the other three behaviours, and on one reading sparql's current behaviour changes - which is task 24's territory, since R2.4 would be the criterion authorising it.
