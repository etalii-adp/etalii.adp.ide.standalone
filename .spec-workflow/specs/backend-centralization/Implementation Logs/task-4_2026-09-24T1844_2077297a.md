WHAT THE BEHAVIOUR WAS BEFORE, because this one is user-visible rather than internal. Mindmap's Save returned void and let AdpFileWriter's exception escape - out of the store, out of the command handler, and out to the caller as an exception rather than a sentence. A user whose map was held open by another program was told nothing they could act on, and no caller could read a failure because there was no result to read. Every other writable store already returned a message; mindmap was the one that threw.

It now returns DocumentSaveResult and, on a refused write, keeps the edit in memory (R3.2, R3.4) - so a retry once the file is writable saves the same edit rather than asking the user to make it again.

SEEN TO FAIL AGAINST THE THROWING PATH. The catch was disabled - `when (false && exception is IOException)` - with the plant confirmed present by grep BEFORE the run rather than assumed from sed's exit code, and the test failed with exactly the defect: "System.IO.IOException : The process cannot access the file because it is being used by another process." The other two tests stayed green, correctly: neither reaches the catch. Plant reverted, three green, mindmap's whole suite 153 passed, dotnet format exit 0.

THE FAILURE IS FORCED RATHER THAN SIMULATED. A FileShare.Read holder makes the writer's temp-then-replace genuinely fail - the same idiom C4Commands.Tests uses - instead of stubbing a failure that might not match what the writer actually does. Windows-only by nature: FileShare is a mandatory lock only there.

TASK 3's GUARD VERIFIED THE CONVERSION'S COMPLETENESS, WHICH THE COMPILER COULD NOT, and this is the result worth carrying into the rest of the specification. Discarding a result is legal C#, so the solution built cleanly with all eight sites still dropping it - the compiler said nothing at all. The guard carried those eight as tracked debt naming this task; converting them emptied the list, and NoProductionCodeDiscardsAStoreSaveResult is green with nothing tracked. GREEN WITH NOTHING TRACKED IS A REAL ABSENCE RATHER THAN A SILENT ONE: it is the difference between "I converted the ones I found" and "there were none left". Had I missed one it would have been named with its file and line.

The seven tracked entries are deleted, as they said they would be. The list itself stays, empty, with a note that this task emptied it: the next conversion group needs somewhere to put its debt, and NoTrackedEntryOutlivesItsFix is what makes an entry expire rather than settle.

ONE THING DELIBERATELY NOT CONVERTED, stated so nobody finishes the job: saving a map the store never loaded still throws InvalidOperationException. That is a programming error rather than an outcome a user can act on - there is no edit to keep and nothing to retry - and R2.8's "skips documents it never loaded" is about Reload, which returns early. Task 10 owns that question. A test pins the throw, so the decision is visible rather than reading as an unfinished conversion.
