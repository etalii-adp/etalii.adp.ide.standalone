A CHANGE BEYOND THE LITERAL WORD OF AN APPROVED DESIGN, SAID PLAINLY RATHER THAN LEFT TO INFERENCE. The design says wardley-map's WardleyPublishResult shape, "moved and shared". It specifies the SHAPE - an error and a warning, both empty on success - and the kind was wardley's local choice. This is a sealed record where wardley's was a readonly record struct. The Scrum master ruled the change after I put three decisions to it; the reason below is measured rather than argued.

WHAT A STRUCT-SHAPED RESULT'S DEFAULT ACTUALLY DOES, measured with a throwaway probe because I had claimed it from reasoning about C# and that is not evidence. All five hold: default.Error is null; asking Failed THROWS rather than answering; Error != "" - the comparison a caller actually writes - is TRUE, so it reads as FAILED; $"{Error}" prints as empty, so the log line of that failure shows nothing wrong; and it stores, passes and compares without complaint.

SO THE HAZARD IS NOT A SILENT SUCCESS - I TOLD THE SCRUM MASTER IT WAS, AND THAT WAS WRONG. It is a FAILURE WITH NO MESSAGE, invisible in logs: the user is told the save failed and given no reason, and the record of it prints as though the field were blank. Worse than what I claimed, and it strengthens the ruling rather than weakening it - but the ruling was accepted on my reasoning, so the correction was owed rather than optional. The rejected alternative was defaulting the strings to empty, which converts a crash into a silent success: the wrong direction for a type whose entire purpose is that failures cannot be ignored.

A NAME COLLISION THE RULING FORCED, which neither of us could see from the proposal: wardley's factory was Failed(error) and the ruled property is Failed. One name cannot be both a property and a method on one type, so the factory is Failure(error) and the property kept the name, because the property is what every call site reads. Recorded in the type's own remarks so the rename is not a mystery to wardley's converted callers.

IT DOES NOT ADOPT THE AdpFileWriteResult IDIOM BESIDE IT, and that is a decision rather than an oversight. EtAlii.Adp.Documents already holds a result vocabulary - AdpFileWriteResult with AdpFileCreated, AdpFileNameTaken and AdpFileWriteFailed - so the namespace now carries two idioms for "what came of writing". That hierarchy is a closed set of CASES BECAUSE ITS CALLERS ANSWER THEM DIFFERENTLY: a taken name means "ask the user for another name", not "report a failure". A save has two outcomes and an orthogonal warning, so a case hierarchy would add a type per outcome without adding a decision. The reason is in the type's remarks rather than only here, because the next person to notice two idioms will be reading the type, not the log.

There is no IsSuccess: two spellings of one question is how thirteen call sites drift apart, and the ignored-result guard needs one obvious thing to look for.
