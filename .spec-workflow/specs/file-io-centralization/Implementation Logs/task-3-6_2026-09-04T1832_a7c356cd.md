# Implementation Log: Task 3.6

**Summary:** SPARQL: SparqlDocumentStore converted to the central shared read, and its tracked allow-list line deleted. The store read a user-authored .rq with File.ReadAllText, which opens at FileShare.Read — the original flaw this specification is named after. Windows sharing is mutual, so a save landing while that read is in flight fails and the author is told their query could not be written. Sparql ships no writer by design and NoWriterSurfaceTests guards that, so no write path was disturbed; the contention is with the text editor the query is authored in, which is exactly the case SharedDocumentReader exists to permit. Read semantics are unchanged: SharedDocumentReader.ReadAllText is a StreamReader over the same default encoding detection as File.ReadAllText and throws the same IOException and UnauthorizedAccessException the existing catch already handles. IMPORTANT CORRECTION for whoever reads the task text: the tasks document's guidance that "databricks and rdf read File.Exists(path) ? ... : \"\" while sparql reads unconditionally" is INVERTED. Sparql checks existence explicitly and returns a NAMED unavailable state ("<file> does not exist. Queries are authored in a text editor; this diagram draws an existing .rq file."), while databricks is the one that collapses missing-to-empty inline. Both check; they differ in what they return. An agent "preserving unconditional reading" would delete sparql's File.Exists block — and since FileNotFoundException is an IOException it would be caught and rendered as "could not be read", leaving the suite green, the guard silent, and only the message that distinguishes a missing file from a broken one lost. That block was left untouched, so Requirement 2.5's unreadable-versus-unparseable distinction survives intact. All three guard combinations were seen rather than assumed (see artifacts). The allow-list conflict with tasks 3.4 and 3.5 was the trivial one the tasks document predicted; resolved by keeping every deletion, which empties the raw-read category entirely — the section header comment was removed with the last entry, since a heading describing an empty category misleads. Entry count is unaffected, so 3.7's "lost exactly six tracked lines" check still holds.
