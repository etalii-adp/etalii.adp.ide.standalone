# Implementation Log: Task 18

**Summary:** Property commands, and the editing machinery every later command uses. A gesture of the table becomes model changes (KnowledgeEdits.Plan), which are written by one command (KnowledgeEditCommand, through the FBL runtime on a copy of the body, all or none, inverse = RestoreDocumentCommand with the bytes before) and shown at once through KnowledgeProjection while the write is queued (write-behind, ruled 2026-10-09). Properties: add at the end or left/right of another (also placed in the view's own column order where it has one), rename (refused for an empty name or a name another property has, ignoring case), duplicate (type and options under new ids, never the title, no values), delete (cells, columns, sorts and conditions cascade in the binding; a view grouped by it is ungrouped in the same step; the title is refused). Seen to fail: a delete that leaves the view's grouping, and a rename accepted for a duplicate name (commit 6945970b1, sabotage run with 12 failures across six planted defects). DEVIATIONS: (1) one command type carrying the changes rather than one command and handler per gesture - the gesture's meaning is in KnowledgeEdits, and redo replays the changes; (2) a refusal is the edit's answer, shown on the frame's refusal line, not a ProposeInput prompt; (3) no SetTitleProperty gesture and no separate MoveProperty - order is per view (moveColumn); (4) a declared binding cannot add at a position, so a placed add is Add then Move in one step; (5) duplicating copies no cell values: each cell is one planned change that re-reads the body, which does not scale.
