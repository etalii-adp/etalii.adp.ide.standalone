# Implementation Log: Task 11

**Summary:** A file dialog prompt, the fourth prompt kind; it names no tool type. A provider answers ExecuteAsync with ContextExecutionRequiresFile(ContextFileRequest(Title, Icon, ConfirmLabel, Accepts: Func<string fullPath, bool>, EmptyMessage, Pinned: ContextPinnedFile(Label, FullPath)[])). ContextService builds the tree once with ContextFileTree.Build(rootPath, accepts): folders first then files, by name; only accepted files and the folders leading to them; entries whose name starts with a dot are skipped; an unlistable folder offers nothing. An option's id is the project-relative path joined by '/', which is the value the provider's CommitAsync receives (text is empty). Pinned entries are offered whether or not the predicate accepts them, provided the file exists inside the project. The offered ids are kept on ContextInteraction.Offered, and SubmitInteraction refuses a value outside the set with 'That file cannot be chosen here.' before the provider runs, leaving the dialog open. Wire: context.proto FileDialogPrompt { title, icon, confirm_label, files, pinned, empty_message } reusing ContextOption, as ContextPrompt member 6 (file_dialog). Client: FilePromptDialog.tsx maps the prompt onto the existing ChoicePromptDialog (pinned first, then the tree, no name field), so the keyboard paths, roles and refusal handling are the choice dialog's; ContextPromptHost renders the 'fileDialog' case and lists it in RENDERABLE_PROMPTS. DEVIATION: the task names 'the interaction store' as a file to change; the store is unchanged, the offered set lives on the ContextInteraction record it already holds. Seen to fail: the tree built without the predicate (3 tests), the submission check disabled (6 cases), and the host before it knew the kind (the host test failed with no tree rendered). Not covered: a very large project is walked in full on every prompt (no cap, no cache); the dialog shows file names only, with no tool-type icon per file.
