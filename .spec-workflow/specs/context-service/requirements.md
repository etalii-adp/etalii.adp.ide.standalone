# Requirements Document

## Introduction

This spec adds a **context service**: one backend-owned, per-connection record of *what the user currently has selected*, with a gRPC `Select` call through which any surface reports a selection, and a `Watch` server-stream through which any interested party — on the client or inside the backend — learns about it. The first source feeding it is the workspace explorer from [`project-root-folder-explorer`](../project-root-folder-explorer/requirements.md): whenever the user selects a file or folder there, its path (the entry's location relative to the project root, resolved by the backend) together with its `ShortGuid` id is forwarded to `Select`. The selection message itself is deliberately generic — a **source** (which surface produced it), a **path** (where it is, as hierarchical segments: a file, an element inside a diagram, an index in a list), an **id**, and a `oneof` that is either **none** (a plain selection), an **action** (the gesture behind it: activate, open a context menu, preview, …) or a **child** selection (what is selected *inside* the selected thing, recursively) — so that a diagram canvas, a ribbon, a search result list, or a future diagram-type module can feed it without the contract, the service, or any existing consumer changing.

The service is meant to take a central role: the Property Grid, the ribbon's contextual command buttons, "open the selected file in a diagram tab", per-diagram undo/redo, the Errors & Warnings panel and the context-action mechanism of [`rename-files-and-folders`](../rename-files-and-folders/requirements.md) all need to know *the current selection*, and today none of them can. The only thing resembling a selection in the codebase is `ExplorerTreePanel`'s private `focusedKey` React state, which never leaves that component.

A thorough search of the current specs, protos, backend and client (summarised in *Existing functionality this service replaces or absorbs* below) found one existing mechanism that overlaps with this one — the context-action RPCs (`DiscoverActions`, `ExecuteAction`, `ProposeInput`, `SubmitInteraction`, `CancelInteraction`) that [`rename-files-and-folders`](../rename-files-and-folders/design.md) placed on `HierarchyService` only because that service already held the one per-connection stream a browser can be pushed anything over. Their `ContextSource` id vocabulary (`context.proto`) is exactly how this spec identifies a selected thing, and its `ContextScope` stays the provider-routing key behind the scenes; this spec adopts both as-is, hosts the new `Select`/`Watch` RPCs in a dedicated `ContextService`, and migrates the existing context-action RPCs and prompt channel onto that same service so the hierarchy service goes back to being about the hierarchy only.

## Alignment with Product Vision

- **"A familiar surface"** ([product.md](../../steering/product.md)): in VS Code, Rider and Visual Studio, selecting something in one tool window drives every other one — the Properties window follows the selection, toolbar commands enable and disable against it, the editor opens it. That single shared "current selection" is what makes an IDE feel like one product rather than a set of unrelated panels; this spec introduces it for ADP.
- [tech.md](../../steering/tech.md)'s **frontend-backend synchronization** principle ("state changes flow from backend to client as a gRPC stream") and its note that the backend already "remembers the state of the view in the client per connection": a connection's selection is the same kind of per-connection client state as its view state, and is kept in the same place — the backend — for the same reason: so backend-side logic (context-action providers, future property providers, diagram modules) can act on it without a round trip.
- tech.md's **"The backend is the sole owner of reading/writing diagram files; the web client never touches the filesystem directly"** and `rename-files-and-folders` design's deviation 3: the client identifies what it selects by **id**; the project-relative path it sends alongside is verified against (or filled in from) what that id resolves to inside the project root, never trusted as a locator on its own, and an absolute filesystem path is never accepted from, or sent to, the browser.
- [structure.md](../../steering/structure.md)'s **core-vs-diagram-type-plugin dependency direction**: the selection record is scope-agnostic data; a diagram-type module can publish selections of its own kind of id and path, and subscribe to everyone else's, without core code knowing that module exists, which is the same seam `IContextActionProvider` already established.
- [short-guid](../../archive/specs/short-guid/requirements.md): selections reference what they refer to by the same `ShortGuid` the referenced thing already carries (hierarchy entries today; diagram elements and others later), rather than introducing a second identifier representation.
- [`reusable-context-menu`](../../archive/specs/reusable-context-menu/requirements.md) / [`rename-files-and-folders`](../rename-files-and-folders/requirements.md) **"don't reinvent, integrate"**: the existing `ContextSource` message is reused as the selection's id and `connection.proto`'s existing `Path` as its path, rather than defining parallel types.

## Requirements

### Requirement 1 — A dedicated context service

**User Story:** As a developer building IDE features, I want one backend gRPC service that owns "what is currently selected on this connection", so that every panel, command and backend provider reads the same answer instead of each surface wiring private callbacks to the others.

#### Acceptance Criteria

1. WHEN the backend starts THEN the system SHALL expose a gRPC service dedicated to context — `ContextService` — separate from `HierarchyService`, `ProjectService`, `DiagramService` and `AuthenticationService`, defined in the shared `src/api/` contract folder alongside the existing `context.proto` vocabulary it builds on.
2. WHEN `ContextService` is defined THEN it SHALL offer at least a unary `Select` call (Requirement 2) and a server-streaming `Watch` call (Requirement 4); both SHALL work over gRPC-Web from the browser, i.e. neither SHALL require client-streaming or bidirectional streaming, consistent with the constraint `rename-files-and-folders` design already established.
3. WHEN a `ContextService` call is made THEN the system SHALL authorize it the same way `HierarchyService` calls are authorized today (session interceptor plus `TryResolveRootPath`-style project authorization), so a selection can only be made or watched within a project the caller may access.
4. WHEN the context service keeps state THEN it SHALL keep it strictly **per connection**, identified by the same client-generated `watch_id` the hierarchy calls on that connection use, and SHALL never share it with another connection — not even one from the same user viewing the same project — following the 1:1-per-`watch_id` discipline `IHierarchyModelStore` and `IContextInteractionStore` already enforce.
5. WHEN the `Watch` stream for a `watch_id` ends (client closes it, navigates back to the project grid, or the connection drops) THEN the system SHALL discard that connection's selection and every other context state held for it, so nothing outlives its connection.

### Requirement 2 — The select message: source, path, id, and none / action / child

**User Story:** As a developer adding a new surface, I want to report a selection with a message that says *where it came from*, *where the thing is* (as a path), *which one*, and — in one place — either *nothing more*, *what the user did to it*, or *what is selected inside it*, so that one recursive message covers a plain selection, a gesture, and a nested selection without the contract growing a field per case.

#### Acceptance Criteria

1. WHEN a client reports a selection THEN the system SHALL accept a `Select` request carrying the `project_id`, the connection's `watch_id` and one `ContextSelection` message; the request SHALL carry nothing surface-specific beyond those.
2. WHEN a `ContextSelection` is expressed THEN it SHALL consist of a **source**, a **path**, an **id**, and a `oneof` with exactly three alternatives:
   - `none` — this is a plain selection, nothing else is meant by it;
   - `action` — a `ContextSelectionAction` (Requirement 9) saying what the user did to the selected thing;
   - `child` — a nested `ContextSelection` describing what is selected *within* the selected thing.

   The `child` alternative is the same message type, so nesting is recursive: the child again carries a source, a path, an id, and a `oneof` of `none` / `action` / `child`. The innermost element of the chain is the one that carries the action, if any; the chain as a whole is the selection.
3. WHEN the **path** is expressed THEN the system SHALL reuse `connection.proto`'s existing `Path` message (`repeated string segments`) as the hierarchical locator of the selected thing, so that anything that can be presented as a path — a file or folder under the project root (`["docs", "design.mm"]`), an element inside a diagram (`["root", "Architecture", "Backend"]` for a mindmap node), an item in a flat list (`["3"]` for the fourth problem in the Errors & Warnings panel), a location in a file (`["42"]` for a line) — is expressed with one shape. A flat list is simply a path of one segment. The path is the selection's *where*; the id (Requirement 2.4) is its *identity*: the path is what humans and path-based consumers read, the id is what survives a rename (`project-root-folder-explorer` Requirement 2.5).
   - What a `child` means is **decided per kind of parent**, by the resolver registered for the parent's `ContextSource` member (Requirement 2.6): it declares whether children of that kind are *contained* or *referenced*, or whether nesting under it adds no value and is rejected.
     - **Contained** (a folder's entry, a file's element, an element's sub-element, a file's location): the child's path is **relative to its parent's path**, so concatenating the segments of the chain from the outermost level inward yields one full path — exactly the semantics `connection.proto` already gives `Path` ("the leading segments resolve to a file within the workspace; any additional segments address a location/sub-scope within that file"). A chain *explorer `["docs","design.mm"]` → canvas `["root","Backend"]`* is therefore the same location as the `Path` `["docs","design.mm","root","Backend"]` a `DiagramService.Connect` would be opened with.
     - **Referenced** (a problem in the Errors & Warnings list pointing at a file, a mindmap node's code-artifact link pointing at a file): the child's path is project-relative in its own right and does **not** concatenate with the parent's; the chain says "X, which refers to Y", and the resolver for X's kind vouches that X actually refers to Y.
     - **Not nestable** (nothing sensible lives "inside" the thing, e.g. a ribbon command): a `child` under it is rejected per Requirement 2.6.
     The explorer's `entry_id` resolver (this spec) declares folders as containing entries; every other kind is declared by the spec that adds it.
   - Paths in a selection SHALL always be project-relative (the outermost level) or parent-relative (a child); an absolute filesystem path SHALL never be accepted from, or sent to, a client.
   - The former `ContextScope` enum is **not** part of the selection. It remains `context.proto`'s routing key for context-action providers (`IContextActionProvider.Scope`), and the backend SHALL derive it, per level, from the `ContextSource` member used for the id (an `entry_id` routes to `HIERARCHY` providers; a future `element_id` to that diagram type's providers) — a client never states a scope.
4. WHEN the **id** is expressed THEN the system SHALL reuse `context.proto`'s existing `ContextSource` message (today: `entry_id`, a `ShortGuid`), so a selection names the selected thing exactly the way a context action already names its target; a future kind of thing (a diagram element, a search hit, a location in a file) is added as one more `oneof` member of `ContextSource`, not a new message.
5. WHEN the **source** is expressed THEN the system SHALL identify the surface that produced the selection as a new `ContextSelectionSource` value (e.g. `EXPLORER`, with `DIAGRAM_CANVAS`, `SEARCH`, `PROBLEMS`, `TOOLBOX`, `RIBBON`, `PROPERTY_GRID` reserved for later surfaces) distinct from `ContextSource`, so a consumer can tell "the explorer selected entry X" from "the canvas selected entry X" even when path and id are identical — e.g. so the explorer does not re-react to a selection it produced itself. A `child` carries its own source, because a nested selection may have been produced by a different surface than its parent (a file selected in the explorer, an element inside it selected on the canvas).
6. WHEN a `Select` request names an id the backend cannot resolve on that connection (unknown `watch_id`, an entry id belonging to another connection or project, or an entry that no longer exists) — at any level of the chain — THEN the system SHALL reject the whole request with a clear, non-revealing error and SHALL leave the connection's current selection unchanged, consistent with `TryResolveTarget`'s "unknown and unauthorized are answered the same way" rule; a partially resolved chain SHALL never be recorded.
   - WHEN a level's id is of a kind the backend can resolve to a path itself (today: an `entry_id`, through the connection's own `HierarchyModel`) THEN the system SHALL verify the client-supplied path against the resolved one and reject the request on a mismatch; the id is authoritative, the path is checked, never trusted. The backend MAY accept an empty path for such a level and fill it in from the id on the echoed message (Requirement 4.3), so the explorer does not have to recompute a path it does not otherwise keep.
   - WHEN a level's id is of a kind the backend cannot resolve yet (no resolver registered for that `ContextSource` member) THEN the system SHALL reject the request rather than record an unverified level — a new kind of thing becomes selectable by registering its resolver (Non-Functional: Dependency direction), not by the backend trusting paths.
7. WHEN a client wants to clear the selection (nothing is selected any more) THEN the system SHALL accept a `Select` request whose `ContextSelection` is absent, recording "no selection", rather than requiring a separate RPC or a dedicated action value.
8. Each level of a `ContextSelection` SHALL carry exactly **one** id; multi-selection is not in scope for this spec, matching `rename-files-and-folders` Requirement 4.4's single-entry rule. The message SHALL be designed so a later spec can extend it to several ids at a level (e.g. by making the id repeated) without renaming or replacing it.
9. WHEN the backend records a selection THEN it SHALL record the entire chain, and WHEN it resolves it THEN each level SHALL be resolved in the context of its parent according to the parent kind's nesting rule (Requirement 2.3) — a hierarchy-entry child of a folder parent must actually be contained in that folder; an element child of a file parent must belong to that file; a file child of a problem parent must be the file that problem refers to — so a consumer reading the chain can trust the containment or reference it expresses, and a concatenated path, where the rule is containment, is a real location.

### Requirement 3 — Explorer selections are forwarded to `Select`

**User Story:** As a user, I want the file or folder I click or arrow onto in the explorer to become "the current selection" everywhere in the IDE, so that the properties panel, commands and editors follow what I'm looking at.

#### Acceptance Criteria

1. WHEN the user selects an entry in the explorer tree — by clicking it, by moving keyboard focus onto it with the arrow keys (`rename-files-and-folders` Requirement 1), or by right-clicking it (which also focuses it, that spec's Requirement 3.1) — THEN the client SHALL call `Select` with source `EXPLORER`, that entry's project-relative path (its name segments from the root, as the tree already knows them through its parent chain — or empty, letting the backend fill it in per Requirement 2.6), that entry's `ShortGuid` id and the alternative matching the gesture (`none` for click and arrow-focus, action `CONTEXT_MENU` for right-click / `Shift+F10` / the context-menu key, action `ACTIVATE` for double-click / `Enter` — Requirement 9), for the connection's `watch_id`.
2. WHEN the backend accepts an explorer selection THEN the system SHALL resolve the entry id, through that connection's own `HierarchyModel`, to its location under the project root, verify (or fill in) the path per Requirement 2.6, and SHALL record the selection with its id, its project-relative path and its kind (file/folder) — so consumers (backend providers and, per Requirement 4.4, clients) receive the path and the id together, as the explorer's contribution to the context, rather than having to resolve it again. The backend keeps the absolute path only in its own store (`ContextTarget.ResolvedFullPath`, as today) for providers.
3. WHEN the selected entry is renamed, moved or deleted on disk (`project-root-folder-explorer` Requirement 4) THEN the system SHALL update or clear the recorded selection accordingly — its id stays the same across a rename (that spec's Requirement 2.5), so only its path changes; a delete clears the selection — and SHALL notify watchers (Requirement 4) of the change without the client needing to call `Select` again.
4. WHEN the explorer moves focus purely for navigation in quick succession (e.g. holding `ArrowDown`) THEN the client SHOULD coalesce the resulting `Select` calls (e.g. by debouncing with the existing `useDebouncedValue` hook, or by only sending the last of a burst) so the backend is not asked to record every intermediate row; the final resting entry SHALL always be reported. Only `none` selections are ever coalesced: a `CONTEXT_MENU`, `ACTIVATE` or `PREVIEW` select SHALL bypass the debounce and be sent immediately, flushing (or superseding) any pending `none` for the same entry, so a right-click or double-click is never delayed by preceding keyboard navigation.
7. WHEN the user right-clicks (or presses `Shift+F10` / the context-menu key on) an entry whose actions have already arrived on the context stream for a preceding `none` selection of that same id THEN the explorer MAY open the context menu from those actions immediately while the `CONTEXT_MENU` select is in flight, and SHALL replace the menu's groups if the stream's answer to the `CONTEXT_MENU` select differs — preserving today's instant-open feel without a client-side key→action table.
8. WHEN the user double-clicks or presses `Enter` on a **folder** entry THEN the explorer SHALL toggle its expand state locally, as it does today, and SHALL report the gesture as `ACTIVATE` all the same; a consumer that opens files (Requirement 8.1) ignores `ACTIVATE` on a folder by checking the pushed kind (Requirement 4.4).
5. WHEN the explorer tree loses the selected entry from its rendered set (the entry's parent folder is collapsed, or the entry is removed by a pushed hierarchy change) THEN the client SHALL NOT silently keep reporting it as selected — a collapsed parent keeps the selection (the entry still exists), a removal clears it via Requirement 2.7, matching what the backend does independently under Requirement 3.3.
6. WHEN the explorer tree unmounts (back to the project grid) THEN the client SHALL close its context `Watch` stream, and the backend SHALL discard the selection per Requirement 1.5; no explicit clearing `Select` is required.

### Requirement 4 — Watching the context

**User Story:** As a developer building a panel or a backend feature that depends on the selection, I want to subscribe once and be told whenever the selection changes, so that I never poll and never need a direct reference to the surface that made the selection.

#### Acceptance Criteria

1. WHEN a client opens `Watch` for a `project_id` and `watch_id` THEN the system SHALL start a server stream on which it pushes the connection's context as it changes, and SHALL push the **current** selection (or an explicit "nothing selected") as the first message so a late subscriber is immediately consistent.
2. WHEN the connection's selection changes — by a `Select` call, or by a backend-side update per Requirement 3.3 — THEN the system SHALL push one message to every open `Watch` stream **for that same `watch_id` only**, never to another connection's stream, mirroring the per-connection delivery rule `project-root-folder-explorer` Requirement 4.5 establishes for hierarchy changes.
3. WHEN a selection message is pushed THEN it SHALL carry the same `ContextSelection` chain — source, path, id and the `none`/`action`/`child` alternative at every level — the selection was made with (Requirement 2), with any path the backend filled in or corrected per Requirement 2.6, so a consumer can filter on any of them — e.g. a diagram-tab host reacts only to `ACTIVATE`, a consumer interested in one file filters on the outermost path, the Property Grid shows every selection.
4. WHEN a selection message is pushed THEN it SHALL wrap the client-shaped `ContextSelection` chain in a watch message that adds, **per level**, backend-resolved detail the client cannot or must not supply itself — for a hierarchy entry: its kind (file/folder) and whether it is currently available; for future kinds: whatever their resolver reports — so a consumer such as the Property Grid can show *what* is selected without its own hierarchy lookup. This detail lives on the watch message only, never on `ContextSelection`, so a client cannot send it. The path itself already travels in the selection (Requirement 2.3) and is the same project-relative form `projects.proto` already shows on the project grid; an absolute filesystem path never appears on the wire.
5. WHEN more than one client-side consumer on the same page needs the context (Property Grid, ribbon, diagram pane, explorer) THEN the client SHALL open **one** `Watch` stream per connection and fan it out in-process (e.g. a React context/provider at the workspace-shell level), not one gRPC stream per consumer — the `watch_id` is per connection, and so is its stream.
6. WHEN the `Watch` stream is interrupted THEN the client SHALL reopen it with the same `watch_id`, and the first message per Requirement 4.1 SHALL re-baseline it, the same way `grpc-core-communication` Requirement 6.2 re-baselines a diagram connection.
7. WHEN backend-side code needs the current selection of a connection (a context-action provider deciding what applies, a future property provider) THEN the system SHALL expose it in-process through an injectable store (e.g. `IContextSelectionStore`, a structural sibling of `IContextInteractionStore`), so backend consumers read it directly rather than through their own gRPC stream.

### Requirement 5 — The selection's available actions are pushed, not fetched

**User Story:** As a user, I want keyboard shortcuts and the context menu to be ready the moment I select something, and as a developer I don't want every surface to re-implement "ask for the actions of the focused thing".

#### Acceptance Criteria

1. WHEN a selection is recorded whose (innermost) level routes to a scope that has one or more `IContextActionProvider`s (today: an `entry_id` → `HIERARCHY`, per Requirement 2.3) THEN the system SHALL discover that target's available actions through the existing `IContextActionResolver` and push them on the `Watch` stream alongside the selection (as part of the same message or an immediately following one), in the same `ContextActionGroup` shape `DiscoverActions` returns.
2. WHEN the explorer receives the actions for its own current selection on the context stream THEN it SHALL use those to answer keyboard shortcuts and to populate the context menu, replacing its current per-focus `DiscoverActions` round trip and `actionsByKey` cache (*Existing functionality*, item E); the behaviour `rename-files-and-folders` Requirements 3 and 4 describe — one action implementation behind both triggers, no client-side key table — SHALL remain unchanged from the user's point of view.
3. WHEN the selection's actions change while the selection itself does not (e.g. the selected folder becomes empty, the selected file is locked) THEN the system MAY push a refreshed actions message; it SHALL at least do so when the selection's path changes under Requirement 3.3.
4. `DiscoverActions` SHALL remain available as an on-demand call after its move to `ContextService` under Requirement 6, for any surface that wants the actions of something it has *not* selected (the explorer itself never needs this: a right-click selects first, per `rename-files-and-folders` Requirement 3.1, so its actions always arrive via Requirement 5.1).

### Requirement 6 — Context actions move from `HierarchyService` to `ContextService`

**User Story:** As a developer, I want the context-action RPCs to live on the context service they belong to, so that `HierarchyService` is about the hierarchy only and a new scope's actions don't have to be bolted onto the hierarchy's stream.

#### Acceptance Criteria

1. WHEN this spec is implemented THEN the system SHALL move `DiscoverActions`, `ExecuteAction`, `ProposeInput`, `SubmitInteraction` and `CancelInteraction` from `HierarchyService` to `ContextService`, with their request/response messages unchanged in shape except for their new home and one removal: the `scope` field is dropped from `DiscoverActionsRequest` and `ExecuteActionRequest`, since the backend now derives the provider scope from the `source` id's `ContextSource` member (Requirement 2.3) and a client never states a scope. `rename-files-and-folders`' behaviour is preserved verbatim.
2. WHEN a backend-initiated prompt (`ContextPrompt`: input dialog, confirm dialog, closed) has to reach the client THEN the system SHALL push it on the connection's context `Watch` stream rather than on `WatchHierarchy`; `HierarchyMessage`'s `prompt` member SHALL be removed and `WatchHierarchy` SHALL again stream only hierarchy changes (reverting the widening `rename-files-and-folders` design introduced).
3. WHEN `ContextPromptHost` is rendered THEN it SHALL be driven by the context stream and SHALL live at the workspace-shell level (next to the single `Watch` subscription of Requirement 4.5), not inside `ExplorerTreePanel`, so a prompt raised by an action in any scope can be shown regardless of which panel triggered it.
4. WHEN the move is complete THEN the system SHALL leave `IContextActionProvider`, `IContextActionResolver`, `ContextTarget`, `HierarchyContextActionProvider` and `IContextInteractionStore`'s responsibilities unchanged; only the gRPC surface they are reached through and the channel type prompts are written to change. `ContextInteractionStore.Register` SHALL be called from the context `Watch` stream's lifetime instead of `WatchHierarchy`'s.
5. WHEN an `ExecuteAction` arrives with no `source` (id) THEN the system SHALL apply it to the connection's **current selection** (routing by the current selection's innermost id, per Requirement 2.3), so a ribbon or a global shortcut can say "rename whatever is selected" without first looking the selection up; when a `source` is given it takes precedence, preserving today's explicit-target behaviour.
6. WHEN the existing `rename-files-and-folders` integration tests (`ExplorerContextActionsFlow.Tests.cs`) and explorer unit tests are re-pointed at `ContextService` THEN they SHALL pass with no change to what they assert about user-visible behaviour; tests that assert a prompt arrives on the `WatchHierarchy` stream SHALL be updated to assert it on the context stream.

### Requirement 7 — First consumer: the Property Grid shows the selection

**User Story:** As a user, I want the Properties panel to show what I currently have selected, so that I can see the shared selection mechanism actually works before richer property editing is built on it.

#### Acceptance Criteria

1. WHEN the Property Grid panel is rendered while a selection exists on the connection THEN the system SHALL display, from the context stream (Requirements 2.3 and 4.4), at minimum: the selected entry's name (the last path segment), its project-relative path, its kind (file/folder) and the source that selected it — and, for a chain, each level in order, styled per `diagram-ide-mockup` Requirement 7's theming rules.
2. WHEN nothing is selected THEN the Property Grid SHALL show a clearly intentional "nothing selected" state in place of its current static placeholder, following `diagram-ide-mockup` Requirement 5's placeholder standard, and SHALL keep the existing `futureSpec` hand-off comment for property *editing*, which remains out of scope.
3. WHEN the selection changes THEN the Property Grid SHALL update without any call of its own — it is a pure subscriber of the in-process fan-out (Requirement 4.5).
4. This spec SHALL NOT implement editing any property, nor diagram-element properties — only the display of the explorer's file/folder selection, as proof of the subscription path.

### Requirement 8 — Designed-for consumers that are out of scope here

**User Story:** As a developer planning the next features, I want the context service to be clearly the place they plug in, so that each of them becomes a subscriber rather than a new point-to-point wiring.

#### Acceptance Criteria

1. The spec that implements diagram tabs (`adp-diagram-ide` Requirement 1.2, `project-root-folder-explorer` Requirement 3.4, "select a file node → open it") SHALL be able to open a file purely by subscribing to the context stream for file-kind hierarchy-entry selections whose `oneof` is action `ACTIVATE` (double-click / `Enter`, Requirement 9) — a single click selects (`none`) but must not open, and the alternative is what tells the two apart.
2. The ribbon's *contextual* commands are delivered by this spec (Requirement 10). The mockup's remaining static groups (File: Save/New; Edit: Undo/Redo; View: zoom) stay placeholders for the specs that own those commands (e.g. `diagram-undo-redo` for Undo/Redo); those specs SHALL be able to wire them the same way Requirement 10 wires contextual actions — from pushed actions and `ExecuteAction` against the current selection — with no explorer-specific wiring.
3. The `diagram-undo-redo` spec (Requirement 5: "the diagram it is currently connected to") and `mindmap-diagram` Requirement 12.3 ("navigate to that file within the IDE") SHALL be able to treat "the current diagram" and "navigate to" as, respectively, a diagram-file selection (the outermost level of the current chain) read from, and a file-path activation (file → location chain) written to, this service.
4. A diagram-type module SHALL be able to publish an element selection by adding one `ContextSource` member (its element id), registering a resolver for it (Requirement 2.6) and its own `IContextActionProvider`, with no change to `ContextService`, the explorer, or the Property Grid's subscription code — the same extensibility `rename-files-and-folders` Requirement 2.6 already guarantees for actions.

### Requirement 9 — The `none` / `action` / `child` alternatives and what they are for

**User Story:** As a developer building a consumer, I want a selection to tell me, in one place, whether it is a plain selection, *how* it was made — an activation, a request for a context menu, a preview — or *what is selected inside it*, so that I can react to the intent or to the nesting without every surface wiring a separate callback per gesture or per level, and without the explorer having to know which consumer cares.

#### Acceptance Criteria

1. WHEN the `oneof` is `none` THEN the selection is a plain one: make this the current selection and nothing more. This is what a single click, an arrow-key focus, or a programmatic selection produces; there is deliberately no `SELECT` action value — `none` *is* it.
2. WHEN the `oneof` is `action` THEN it SHALL carry a `ContextSelectionAction` enum value describing the gesture/intent; the initial set SHALL be:

   | Action | Meaning | Typical gesture |
   |---|---|---|
   | `ACTIVATE` | The user wants the selected thing *opened* / its primary action performed. | Double-click, `Enter`, middle-click. |
   | `CONTEXT_MENU` | The user wants to see what can be done with the selected thing. | Right-click, `Shift+F10`, the context-menu key. |
   | `PREVIEW` | Show it without committing to it (transient, non-sticky). | Single click where the consumer supports VS Code-style preview tabs; hover-to-peek. |

   Values reserved for later surfaces, defined now so the numbering is stable but not required to be handled by any consumer in this spec: `DRAG_START` / `DROP` (drag a hierarchy entry onto a canvas, drop a toolbox item on a diagram), `RENAME_REQUEST` (in-place F2-style editing on a canvas rather than a dialog), `FOCUS_ONLY` (keyboard focus moved, but the surface deliberately does not want it treated as a selection — e.g. Tab landing on the tree).
3. WHEN the `oneof` is `child` THEN the selection is nested: the outer level names a container (a folder, a file, a diagram, an element) and the child names what is selected *inside* it, recursively, with the innermost level carrying the action if there is one. A chain therefore reads like a path: *explorer → file X → canvas → element Y → `ACTIVATE`*.
4. WHEN the backend records a selection THEN `none`, `ACTIVATE` and `CONTEXT_MENU` (and any chain ending in them) SHALL all update the connection's *current selection* (the one Requirement 6.5 and backend consumers read); `PREVIEW` SHALL NOT replace the current selection but SHALL be pushed to watchers as a separate, transient message, and a preview ends the moment any later message — another preview, a selection, a clear (absent selection), or a backend-side update — is pushed on the stream; there is no explicit "end preview" call. The backend SHALL echo the whole chain unchanged on the `Watch` stream (Requirement 4.3); it SHALL NOT interpret `ACTIVATE` itself in this spec — what activation *does* is a consumer's decision (Requirement 9.7).
5. WHEN the action is `CONTEXT_MENU` THEN the system SHALL treat Requirement 5.1's pushed actions as mandatory for that message (for `none` they are pushed too, but a consumer may render before they arrive); the pushed message SHALL carry the discovered `ContextActionGroup`s so the explorer can open `reusable-context-menu`'s `ContextMenu` straight from the stream, replacing today's `openMenuFor` → `actionsFor` → `DiscoverActions` sequence in `ExplorerTreePanel`. For a chain, the actions pushed are those of the innermost level — the thing the user actually acted on — while the outer levels give providers the containment context (e.g. "this element, in this file").
6. WHEN a surface needs a *named* context action (e.g. `rename`) to run on what it is selecting — "select this and rename it" — THEN it SHALL NOT encode that as a selection action; it SHALL call `Select` (with `none`) followed by `ExecuteAction` with the action id (or rely on Requirement 6.5's "no source = current selection"). The selection action describes the user's gesture, not a command; commands stay in the context-action mechanism so there is exactly one way to run one.
7. WHEN a later spec adds a gesture that none of the defined actions covers, or a kind of thing that can be nested, THEN it SHALL add one `ContextSelectionAction` value or one `ContextSource` member respectively; existing consumers SHALL keep working because they filter on the sources, paths, id kinds and actions they know (Requirement 4.3), and the explorer SHALL NOT need changing to let a new *consumer* react to an existing action or chain.
8. WHEN a consumer only cares about the outermost level (the Property Grid showing "which file") or only about the innermost (a ribbon enabling commands for the element under the cursor) THEN it SHALL be able to get that by walking the chain client-side; the stream SHALL NOT send separate flattened copies per level.

### Requirement 10 — Context actions in the ribbon

**User Story:** As a user, I want the actions that apply to what I have selected to also appear as buttons in the ribbon — not only in a right-click menu — so that the ribbon is a live, always-visible command surface like the one I know from Office, Visual Studio or Rider, and so that an action I can't currently use is visibly greyed out instead of hidden.

#### Acceptance Criteria

1. WHEN the context stream delivers the actions of the current selection (Requirement 5.1) THEN the ribbon SHALL render them as a **contextual group** (or groups) placed after the mockup's existing static groups (File, Edit, View), with one ribbon button per top-level `ContextAction`, showing the action's icon (`@mdi/font` class, as the menu does) and label — the same icon+label button shape `diagram-ide-mockup` Requirement 2.2 already established for the ribbon, so the contextual buttons are indistinguishable in style from the placeholder ones.
2. WHEN a pushed `ContextActionGroup` contains more than one group (one per provider, Requirement 5.1) THEN the ribbon SHALL render each as its own ribbon group with the existing inter-group separator (`.ribbon-group`'s border), so a diagram-type provider's actions are visually grouped apart from the hierarchy's, mirroring the separator `reusable-context-menu` Requirement 5.2 draws between the same groups in the menu.
3. WHEN a `ContextAction` carries child `items` (a submenu in the menu, `context.proto`'s `ContextAction.items`) THEN the ribbon SHALL render it as a **drop-down button**: the parent's icon and label plus a trailing chevron (`mdi-chevron-down`), which on click (or `ArrowDown`/`Enter`/`Space` when focused) opens the children directly beneath the button. The drop-down SHALL be `reusable-context-menu`'s `ContextMenu`, anchored to the button's bottom-left edge rather than a pointer position, so nested children, separators between child groups, disabled children and keyboard navigation all come for free and behave identically to the right-click menu (that spec's Requirements 3, 4 and 6). The drop-down closes on selection, `Escape`, outside click, or the ribbon re-rendering with a different selection.
4. WHEN an action is reported `available = false` THEN its ribbon button (or drop-down button) SHALL render disabled with the muted treatment `reusable-context-menu` Requirement 4.1 uses for a disabled menu item, SHALL surface `unavailable_reason` as its tooltip (Requirement 4.4 there), and SHALL stay visible rather than being removed — consistent with `rename-files-and-folders` Requirement 2.5's "visible but disabled, not omitted" rule. A disabled drop-down button MAY still open its children (that spec's Requirement 4.3).
5. WHEN the user activates an enabled ribbon button, or an enabled item in a drop-down, THEN the client SHALL call `ExecuteAction` with that action's id and **no `source`**, so it runs against the connection's current selection per Requirement 6.5 — exactly the same call the context menu and the keyboard shortcuts make, one action implementation behind all three triggers (`rename-files-and-folders` Requirement 3.3). Any prompt the action raises arrives on the context stream and is shown by the shell-level `ContextPromptHost` (Requirement 6.3), regardless of which trigger started it.
6. WHEN an action carries a shortcut THEN the ribbon button SHALL show it in its tooltip (e.g. "Rename (F2)"), so the ribbon also teaches the shortcuts; the ribbon SHALL NOT itself listen for those keys — shortcut handling stays with the surface that has focus (`rename-files-and-folders` Requirement 4.5), so the ribbon never fires an action while the user is typing elsewhere.
7. WHEN nothing is selected (Requirement 2.7) THEN the ribbon SHALL keep the contextual buttons it last showed, rendered disabled, rather than removing them — a ribbon that changes shape under the pointer is worse than one holding greyed-out buttons that say what would apply. Only before anything has ever been selected, when there is nothing to keep, SHALL the ribbon render no contextual group at all. A drop-down button held over this way SHALL NOT open, since its children would be about something no longer selected.
8. WHEN the selection changes and the new selection's actions have not yet arrived (the gap between a `Select` and its pushed actions) THEN the ribbon SHALL keep showing the previous contextual group, disabled, until the new actions arrive or a "no selection" message clears it — never flashing empty and refilling on every arrow-key step in the explorer. Combined with Requirement 3.4's coalescing, holding `ArrowDown` in the explorer SHALL produce no visible ribbon flicker.
9. WHEN the contextual group is rendered THEN it SHALL use only the existing ribbon classes and `index.css` custom properties (`.ribbon-group`, `.ribbon-button`, `--color-*`, `--radius`) plus whatever small additions the drop-down chevron and disabled state need, themed for light and dark mode like the rest of the shell (`diagram-ide-mockup` Requirement 7.1–7.3); the contextual buttons SHALL be the same height and padding as the static ones so the ribbon reads as one continuous bar. The placeholder pressed/toggle state the mockup's buttons have (`.ribbon-button-pressed`, `diagram-ide-mockup` Requirement 2.3) SHALL NOT apply to contextual buttons — they are momentary commands, not toggles.
10. WHEN the ribbon is narrower than the sum of its groups THEN the contextual group SHALL NOT push the static groups out of view or wrap onto a second row; it SHALL be the part that overflows, and the overflow SHALL be handled gracefully (horizontal scroll within the ribbon, or collapsing the labels to icons first), so a long list of actions never breaks the shell's layout.
11. The ribbon SHALL be a pure subscriber of the in-process fan-out (Requirement 4.5) like the Property Grid: it holds no selection state of its own and makes no `Select` or `DiscoverActions` call; a right-click in the explorer and a click on a ribbon button are just two renderings of one and the same pushed action list.

#### Use cases this enables

| Use case | What the user sees |
|---|---|
| Select a file in the explorer. | A contextual group with **Rename** and **Delete** appears after View; both enabled. Hover shows "Rename (F2)". |
| Select a folder whose delete is currently not possible (e.g. locked). | Same buttons; **Delete** greyed out with the backend's reason as tooltip. |
| A future diagram-type provider reports "Convert to…" with children (Mindmap, Class diagram, …) for `.mm` files. | A second ribbon group with a **Convert to ▾** drop-down; clicking it opens the same submenu the right-click menu would show. |

Showing the outer file level's actions alongside would need a later spec to push actions per level; the ribbon's group-per-provider rendering (10.2) is already shaped for that. |
| Press Escape / click empty space in the explorer. | The contextual group disappears; the ribbon is the mockup's static bar again. |

## Non-Functional Requirements

### Code Architecture and Modularity

- **Single Responsibility**: `ContextService` owns selection and context interaction only; it SHALL NOT list, watch, rename or delete anything itself — it resolves an id through the resolver registered for that id's kind (the hierarchy's resolver wraps `HierarchyModel`) and delegates actions to providers, exactly as `HierarchyServiceImpl.Context.cs` does today.
- **Modular Design**: the backend gets a `Context/ContextServiceImpl.cs` (the RPC surface) and a per-connection `IContextSelectionStore`; the existing `Context/` abstractions move nowhere. The client gets one context provider at the shell level and small subscriber hooks; no panel talks to `ContextService` directly except through that provider.
- **Reuse over reinvention**: `ContextSource`, `ContextScope` (backend-side routing only), `ContextActionGroup`, `ContextPrompt`, `ShortGuid`, `Path`, the `watch_id` discipline and `useDebouncedValue` are all reused; the only new vocabulary is the selection source enum, the recursive `ContextSelection` message with its `none`/`action`/`child` alternative, and the select/watch messages.
- **Dependency direction**: `Context/` SHALL NOT reference `Hierarchy/` types directly; resolving an `entry_id` to its path and scope SHALL go through an injected resolver registered by the hierarchy side (a per-`ContextSource`-member `IContextSourceResolver`, the selection-side twin of `IContextActionProvider`, Requirement 2.6), so a future kind of id registers its own resolver and `Context/` stays scope-agnostic, per structure.md.

### Performance

- A `Select` round trip plus the resulting `Watch` push SHALL complete fast enough that arrow-key navigation in the explorer feels unchanged; the explorer SHALL keep its own focus state locally and never wait for the backend to move the focus ring.
- Pushing the selection's actions (Requirement 5) SHALL NOT be slower than today's `DiscoverActions` call it replaces; it SHALL NOT walk the selected entry's subtree.
- The in-process fan-out (Requirement 4.5) SHALL not re-render every subscriber on every keystroke-driven selection burst — the coalescing of Requirement 3.4 applies before the stream, and subscribers receive only the resting selection.

### Security

- `Select` and `Watch` SHALL be rejected for a project the session's user may not access, and an id SHALL only ever be resolved through the calling connection's own per-`watch_id` model, so neither call can be used to probe entries of another project or connection.
- The only paths the contract exposes to the client are the project-relative (or parent-relative) `Path` segments of Requirement 2.3, at every level of a chain; absolute paths SHALL never leave the backend.
- Selection messages SHALL only be pushed on the stream of the connection that made the selection.

### Reliability

- IF a `Watch` stream is opened before any `Select` on that connection THEN it SHALL receive an explicit "nothing selected" baseline, not silence.
- IF a `Select` arrives for a `watch_id` with no open `Watch` stream THEN the system SHALL still record the selection (so backend consumers can read it) and SHALL deliver it as the baseline when a stream opens later; such stream-less state SHALL be evicted after an idle timeout unless a `Watch` claims it, exactly as `HierarchyModelStore` already evicts a model created by `ListEntries` that no `WatchHierarchy` attaches to — so a `Select` without a stream can never leak state for the lifetime of the process.
- Stream loss SHALL discard nothing the client cannot rebuild: on reconnect the client re-selects its current focus (Requirement 3.1) if the backend's baseline reports nothing selected.

### Usability

- From the user's point of view nothing in the explorer changes: focus ring, arrow keys, `F2`/`Delete`, right-click and `Shift+F10` behave exactly as `rename-files-and-folders` specified; the visible differences of this spec are that the Properties panel now follows the selection and that the ribbon gains a contextual group of the selection's actions (Requirement 10), with drop-down buttons for actions that have children.
- A consumer that only cares about one path prefix, one kind of id or one source SHALL be able to ignore every other message by filtering on the message's `path`/`id`/`source` fields, without any consumer-specific message types.
