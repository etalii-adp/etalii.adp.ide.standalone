# Implementation Log: Task 4.3

**Summary:** Gated, merged, pushed and watched the pipeline's first successful run, which produced the first release this repository has ever had: tag v0.1.402-alpha at commit 99796eba, with its ZIP. Getting there took fixing two Linux-only defects that no Windows run could reveal, and the release job's own never-executed half had two more.

THE GATE FAILURE THAT KEPT THE PIPELINE RED. src/client/src/viteFsAllow.test.ts resolved its own directory as `new URL(import.meta.url).pathname.slice(1)`, three times. A file URL's pathname always begins with a slash; slicing it off leaves `C:/git/...` on Windows, where the drive letter carries the root, and `home/runner/...` on Linux, where the slash WAS the root. The config loader then reported UNRESOLVED_ENTRY on a path missing its leading slash, so every Linux gate run failed while every Windows run stayed green. Measured rather than reasoned about: for file:///home/runner/.../viteFsAllow.test.ts the old idiom yields a path that path.posix.isAbsolute rejects, and path.posix.resolve then nests it under the runner's cwd. Fixed with fileURLToPath from node:url - the idiom vite.config.ts itself already uses three times - hoisted into one const rather than three copies.

TWO DEFECTS IN THE RELEASE JOB, WHICH HAD NEVER EXECUTED. (1) The workflow ran `cp -r src/client/dist publish/wwwroot` after a publish that already creates wwwroot, and cp treats an existing destination as a parent - so every ZIP would have shipped a second, unreachable copy of the client at wwwroot/dist/. Proven by publishing for real: wwwroot/ comes out with index.html, favicon.svg and assets/ before anything is copied. The copy step is gone; the service project's own PublishClientApp target was always doing the work. (2) That target's ResolvedFileToPublish metadata spelled the destination `wwwroot\%(RecursiveDir)...` - a backslash is a separator only on Windows, on the path deciding where files land on the Linux release runner. Forward slashes work on both, and %(RecursiveDir) still supplies the platform's own separator below it.

THE INTERACTION IS THE LESSON. Had the backslash broken on Linux, the redundant copy would have created a correct wwwroot/ anyway and the run would have gone green while the ZIP carried files named `wwwroot\index.html` - junk that breaks extraction back on Windows. Each defect was the other's alibi. A green release job would not have proved the release was correct; only publishing for real and looking at the output directory found them.

RULED OUT, SO THE NEXT ROUND HAS FEWER PLACES TO HIDE. Two earlier rounds each revealed the next Linux-only failure behind the one fixed, so the question worth answering was how many remained. Measured: 357 relative client imports all resolve with exact case; 1,873 path-shaped string literals across 1,909 sources checked against real on-disk casing, 43 flagged and all one false-positive family (tests' runtime temp `notes.txt` versus Helm's fixture `NOTES.txt`), zero real mismatches; the 4 backslash literals in the backend are deliberate rejection tests, platform-independent because PortableFileNames hard-codes its invalid-character list instead of asking Path.GetInvalidFileNameChars(); and no shipped client source imports a node: builtin at all. One hypothesis was tested and killed rather than reported: the publish target runs `npm ci` in src/client, which holds no package-lock.json, and it exits 0 because npm walks up to the workspace lock.

They do, in Nerdbank.GitVersioning's two shapes: the tag and ZIP spell SemVer2 (0.1.402-alpha) while the assemblies and the login line append the commit as build metadata (0.1.402-alpha+99796ebafe). The entry's expectation said plain equality and now says what is actually true and why. The last half could only be finished by someone signed in to GitHub - the repository is private, this machine has neither gh nor a token, and the unauthenticated API answers Not Found for the Actions and release endpoints, so run status was unreadable and the tag was the only local signal.
