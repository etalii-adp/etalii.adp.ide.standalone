# Implementation Log: Task 4

**Summary:** wardley-map implements the view-delta loop, both halves. The session answered every viewport with nothing, on the local judgement that a bounded space of tens of elements has nothing to virtualize; it now diffs what the reported rectangle admits against what the connection holds, and emits Add for what appeared then Remove for what left - the order both reference implementations use, which the requirements guessed the other way round.

THE FINDING THIS MODULE CONTRIBUTES: TWO KINDS CARRY A PLACEHOLDER POSITION. A naive "is the element's point inside the rectangle" filter is wrong here, and wrong in a way that reads as correct. A link is emitted at (0, 0) because it has no position of its own - it is drawn between its endpoints - and the evolution axis is emitted at (0, 0) because it is the map's frame rather than a thing on the map. Filtering either by that point keeps them only while the reader happens to be looking at the top-left corner and culls them everywhere else, which would mean every relationship in the map vanishing on the first pan. The rule implemented instead: the axis is always kept; a link is kept when an endpoint is kept; a visible component pulls in the components it links to, the way the mindmap mapper pulls in a visible node's parent and children, so a link is never delivered with one end attached to an element this connection was never sent; and an attitude is judged on the rectangle it spans rather than on its corner, so a reader inside a large attitude box does not lose it. This is pinned by its own test.

THE VIEWPORT RESOLVED AT THE CALL SITE, AS EXPECTED. The task anticipated that this module's unusual viewport - the map's own fixed 0..1 space rather than content bounds - would resolve at the call site as it did for canvas-scrollbars, and it did. The canvas draws the 0..1 space into a fixed 1000-unit box, so the conversion is a division by SPACE in a module-local `inMapSpace` beside `scrollAxesOf`, and the shared library learns nothing about the module's units (Requirement 3.4). It deliberately does not clamp to 0..1: the view extends into the margin where the axis labels sit, and a report clamped to the plotted area would cull the elements nearest the edge the reader has just panned to.

EVERY PATH THAT DECIDES WHAT TO SEND USES ONE FILTER. Baseline and the document-changed handler now call the same `Visible()` as `UpdateView`, because a document change diffed against an unfiltered rendering would re-deliver what a viewport had culled. The viewport starts Unbounded and the mapper short-circuits on it, so a connection that never reports one gets exactly what it got before this existed, at no filtering cost. `UpdateView` diffs against `_delivered` rather than re-rendering under the previous rectangle: both agree while the two are in step, and only this one stays right when a document change moved what the connection holds between two reports.

THE BACKEND TEST FAILS AGAINST A RETURN OF NOTHING, PROVEN BY DOING IT. `UpdateView_AnsweringAViewportChange_AddsWhatAppearedThenRemovesWhatLeft` was run against a temporarily sabotaged `return []`: exit code 2, one failure, that test named. The sabotage was asserted present in the written file before the run - an edit that silently matches nothing leaves a suite passing and reads as robust code. The file was restored and the sabotage marker confirmed gone.

TWO STALE ASSERTIONS INVERTED RATHER THAN DELETED. `UpdateView_SendsNothing_BecauseTheWholeMapIsAlreadyThere` became `UpdateView_WithAnUnboundedViewport_SendsNothing` - the same coverage, with the superseded rationale replaced by the one case where answering nothing is still right. `useWardleyStream`'s "exposes no reportView, by design" became a test that the hook exposes it, because the canvas destructures that name and a silently missing one would leave the loop wired to undefined.

The class remarks and the hook's doc comment, which both argued for declining the mechanism, now describe what the code does.
