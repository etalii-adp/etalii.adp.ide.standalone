# Tasks Document

One worktree for the whole spec: `.claude/worktrees/rename` — deliberately short, because the Windows MAX_PATH failure mode (apphost never produced, `dotnet test` reporting zero tests) is traced to long worktree names. Set `MSBUILDDISABLENODEREUSE=1` and `DOTNET_CLI_USE_MSBUILD_SERVER=0` before gating: concurrent MSBuild nodes have been diagnosed as the cause of 0xC0000005 host crashes on this machine. Capture every gate's exit code **into a variable before any pipe** — in a pipeline `$?` is the last command's status, so `dotnet test … | tail` reports `tail`'s success and a crashed or zero-test run reads as green.

**The order is the design's dependency order**, and it is not arbitrary. The contract comes first because nothing else can be written against a field that does not exist; the shared entry hook comes second because it is a pure refactor whose only proof is that the existing dialog tests stay green, and doing it before there is a second caller keeps that proof clean; the placement registry comes before the editor because the editor's tests need somewhere to be placed. Mindmap adopts before C4 because a mindmap node is the plainest possible case — one boxed label, one authored value — and C4 is the one that exercises everything the design had to reason about.

**Three rules that apply to every task below, stated once here.**

- **A canvas supplies geometry and text, nothing else** (Requirement 1.2). If a canvas cannot adopt the editor without adding a prop to it, widening `LabelPlacement`, or changing behaviour in `src/client/src/canvas/label/`, that is a **stop-and-report**, not a thing to work around. The permitted outcomes are that the shared piece grows **once, centrally**, serving every consumer, or that the canvas is documented as unable to use it with the specific reason. A private inline editor for one canvas is forbidden, and task 7's guard exists to make that stick.
- **An unmarked prompt must be byte-for-byte what it is today** (Requirements 2.2, 7.4). Every task that touches the prompt path proves this rather than assuming it: the 45-odd input sites that are not renames are the majority of the feature's blast radius, and none of them should be able to tell this specification happened.
- **Tests are named for the defect each catches.** "Asserts the inline editor works" is the phrasing to avoid: an editor that renders, focuses and then silently drops its commit passes that test.

  - Backend: `RenameActionId` **and** `RelabelActionId` set the marker; `SetTechnologyActionId`, `SetProtocolActionId` and `EditDescriptionActionId` do not — a technology and a protocol are not the label, and a description that is not shown on the element is not either.

Say so in a comment where the fallback lives, rather than leaving a future reader to discover it.
  - Tests: the relationship-technology test above; **an element rename works inline**; **a relationship label editor is placed at the midpoint** (against the fallback estimate).
