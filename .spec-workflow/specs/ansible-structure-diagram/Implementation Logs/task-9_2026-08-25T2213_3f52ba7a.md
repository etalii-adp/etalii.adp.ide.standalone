# Implementation Log: Task 9

**Summary:** AnsibleYaml.Read(fullPath, relativePath) returns AnsibleYamlDocument (root node, null for an empty file - valid YAML with nothing in it, not a failure) or AnsibleYamlUnreadable (an AnsibleYamlFailure carrying the parser's own message and line). Never throws for bad input: IOException/UnauthorizedAccessException, YamlException and any other exception all become failures. Modelled as an abstract AnsibleYamlResult with two sealed records beside it, following the DiagramRouting / ContextLevelResolution shape already in this repo. Two decisions worth recording. (1) The representation model rather than typed deserialization: Ansible's schema is loose - a roles: entry is a string or a mapping, a when: is a string or a list - so a strong binding would reject documents Ansible itself accepts, and walking nodes keeps YamlNode.Start, which is the line a problem points at. (2) A private Reason() strips YamlDotNet's "(Line: 7, Col: 3): " prefix, because the line travels as a number and repeating it in the text would show the reader a position beside a row already labelled :7. Files are opened FileAccess.Read/FileShare.ReadWrite so reading never contends with the text editor the user is fixing their YAML in - which is the only editor this diagram type ever expects them to use, and there is a test for it. 14 tests: parse, line marks (asserting the two plays land on lines 2 and 4), a malformed file's message and line with no "Line:" prefix, an empty file, a missing file, the no-lock property, and - the payoff - two fixture sweeps proving every YAML file in infrastructure/ and unconventional/ parses and that unparsable.yml is the ONLY file in broken/ that does not. That is the machine check the task-1 readme promised would arrive at task 9; the hand-written fixtures are now known to be well-formed YAML, though still not verified as good Ansible. Verified: build 0 errors, module tests 14/14.
