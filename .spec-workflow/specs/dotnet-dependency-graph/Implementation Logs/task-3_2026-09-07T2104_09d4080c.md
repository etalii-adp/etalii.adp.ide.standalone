# Implementation Log: Task 3

**Summary:** ProjectReader plus ProjectReferenceReading / PackageReferenceReading / ProjectReading (Requirements 3.2, 3.3, 3.6). One fixture project nested under two Directory.Packages.props files exercises the whole mechanism: the upward walk, MSBuild's nearest-wins rule, a version pinned on the reference, a version written as a <Version> child rather than an attribute, and a package no props file names. Multi-targeting is read from TargetFrameworks as well as TargetFramework, because a reader knowing only the singular reports nothing for a multi-targeted project - an absence indistinguishable from "declares none".

Central package management is this repository's own arrangement (ManagePackageVersionsCentrally, bare PackageReference lines), so the versionless reference is the ORDINARY case here rather than an edge case, exactly as the task said. A reference whose version cannot be resolved still becomes an edge with Version null - not discoverable, which Requirement 4.4 renders differently from blank - because dropping it would misrepresent the project while an edge with an unknown version is the truth.

Two mechanisms seen to FAIL first: with the upward walk inverted so the outermost props file wins, the nearest-wins test went red (that defect would report a version the build does not use - a wrong answer wearing the same confidence as a right one); with versionless references dropped, the never-omit-an-edge test went red. 24/24 green after restoring.

The module readme (src/diagrams/dotnet-dependency-graph/readme.md, the first module-level readme in the tree - no other module carries one) states what the reader does NOT resolve: MSBuild conditions, Import elements, unexpanded properties inside a version or include, and transitive packages. That list matters more in a derived graph than an authored one, because a missing edge here looks exactly like a dependency that is not there. Worktree commit febd2c51 on claude/ddg.
