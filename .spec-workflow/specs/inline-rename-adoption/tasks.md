# Tasks Document

One worktree for the whole spec: `.claude/worktrees/adopt` — short, because the Windows MAX_PATH failure (apphost never produced, `dotnet test` reporting zero tests) is traced to long worktree names. Set `git config --worktree user.name "agent-<N>-inline-rename-adoption"` the moment you create it. Set `MSBUILDDISABLENODEREUSE=1` and `DOTNET_CLI_USE_MSBUILD_SERVER=0` before gating. Capture every gate's exit code **into a variable before any pipe** — in a pipeline `$?` is the last command's status, so a crashed or zero-test run reads as green.

**One developer owns this specification through every task, in series.** No other developer works on it until it is done. The tasks are independently landable, and that buys **ordering freedom and clean merges** — take one, land it, let the pattern harden before the next — **not extra hands**. This is worth stating because `view-delta-adoption` sits one directory away with a nearly identical shape, and it ran seven adopters across seven agents in an afternoon before the ownership rule was read carefully. Do not infer its staffing from its structure.

**The order is the schedule, not a convenience.** Task 1 is the shared half and everything else depends on it. Tasks 2 to 5 are the four adopters that need no prerequisite, cheapest first, so the pattern the later ones copy is a landed one. Tasks 6 and 7 are wardley, last on purpose: it is the largest piece and the only one with a prerequisite of its own, so if this specification is ever cut short what is dropped is the module needing the most work rather than four needing the least.

**Three requirements are satisfied by this document's own shape rather than by any task in it**, and the coverage diff will otherwise report them as unclaimed: **1.5** (the in-scope set follows from Requirement 1's criteria applied per module, not from a list), **8.1** (one task per module rather than per canvas, which is why databricks is one task for three readings) and **8.3** (the modules needing no prerequisite come first). Nothing to implement; stated so the diff's answer is a real one.

**Three rules that apply to every task below, stated once here.**

- **Two edits and no more.** An adopter marks its qualifying prompts and registers a placement resolver. If a canvas cannot adopt without changing `src/client/src/canvas/label/` or `InlineLabelPlacementContext`, that is a **stop-and-report** (Requirement 2.2), not something to work around — the permitted outcomes are that the shared piece grows once, centrally, or that the canvas is documented as unable with its specific reason.
- **A test written for a defect is accepted only when it has been seen to fail against that defect.** On `inline-rename` three tests passed against broken code — one whose window React batched away, one whose blur jsdom never delivered, and one that omitted `StrictMode`, outside which the bug could not exist — and the third was deleted rather than kept. Perturb, watch it fail, restore, then keep it.
- **Mark only what the module draws.** Before marking any prompt, confirm its value **is** the text on screen. Requirement 1 is the test; the databricks task below carries a worked example of a label that looks markable and is not.
