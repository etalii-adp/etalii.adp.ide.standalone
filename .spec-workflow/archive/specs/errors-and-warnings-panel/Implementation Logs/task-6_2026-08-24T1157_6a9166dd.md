# Implementation Log: Task 6

**Summary:** Implemented ProblemMaintenance and StartupRevalidation. Maintenance keeps one FileSystemWatcher per Track()ed root (FileName|DirectoryName|LastWrite|Size - content matters here, unlike the hierarchy's watcher): a changed/created file is enqueued and coalesced per root behind a settle timer (default 500ms), then re-validated alone via a File-scope ProjectValidator run whose covered paths come from the routing (so a pair that became clean still clears its old entries); a deleted file gets store.Remove at once, plus a revalidation of a surviving sibling registration; a rename becomes store.Move so problems follow the file; AdpFileWriter scratch files are filtered, and a scratch-file publish-rename is read as the create it is. DESIGN DEVIATION (recorded in the class remarks): maintenance watches the filesystem itself rather than subscribing to HierarchyModel.EntryChanged - hierarchy models are per-connection, id-keyed and idle-evicted, while the problem set is one per project; the design assumed a central model that does not exist. StartupRevalidation is an IHostedService draining a sequential queue of IProblemStore.KnownRoots() (a new interface member: roots are discovered from the per-project caches, since IProjectStore has no cross-user enumeration); Prioritize(root) front-inserts an opened project; a missing root is warned and skipped once; StopAsync cancels. 9 unit tests: one changed file = one validation (validator call count proves no traversal), delete drops, rename moves without removing, coalescing, .txt ignored, sequential order, prioritized jump, missing-root skip, stop abandons queue. 419/419 backend green, style clean.
