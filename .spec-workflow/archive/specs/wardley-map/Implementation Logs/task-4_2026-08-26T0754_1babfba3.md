# Implementation Log: Task 4

**Summary:** WardleyDocument: a line-preserving concrete syntax tree for .owm, with ReplaceLine, InsertLine and RemoveLines splicing one range and leaving every other line as the bytes it arrived as. Requirement 3.3's forward compatibility falls out of this by construction rather than being worked for - a statement the module does not model is simply a line it never splices. 1-based uint line numbers via WardleyLine, matching DiagramProblemLineLocation; the reference OWM parser numbers from 0, so that conversion happens once where its output is read. A BUG WAS FOUND, AND IT WAS IN THE PATTERN BEING COPIED, NOT IN NEW CODE. A test asserting that a mixed-terminator document round-trips failed: expected "...[0.5, 0.5]\n", actual "...[0.5, 0.5]\r\n". C4Document - the approved design's named reference - holds lines as bare strings and rebuilds text with string.Join(Newline, _lines) where Newline is whichever terminator the file used more often, so every terminator in the output becomes the dominant one. Requirement 3.1 carries no "unless the file mixes them" clause, and a file edited on two platforms or merged from two branches mixes them routinely. The test was right and the implementation was wrong. WardleyDocument therefore holds terminators PER LINE via a WardleyDocumentLine(Text, Terminator) record, ToText is string.Concat over text+terminator, ReplaceLine keeps the line's own terminator, and Newline now means only what a NEW line is given. InsertLine appending past an unterminated final line must first terminate that line or the two run together - the one case where it changes a line it was not asked to change, and the alternative is a corrupt document. An empty document yields no lines at all so "" round-trips as "" rather than as one blank line. GUARD ADDED per CLAUDE.md: mixed-line-endings.owm joins the corpus, certified against the real parser like the rest, and is covered by the byte-identical round-trip Theory that failed before the fix. THE SAME DEFECT EXISTS IN C4Document by construction - its _lines is a List<string> with nowhere to keep a per-line terminator - and c4-diagrams Requirement 3.1 makes the same unconditional promise. Reported rather than fixed here, since that is another module's spec to amend; a background task carries the worked fix and a note to check whether azure-pipeline-diagram's planned PipelineDocument inherits the same shape. 21 tests, including the corpus round-trip as a Theory over every fixture, a Corpus_IsNotEmpty guard so a corpus that failed to copy to the output folder cannot report as green rather than as nothing having run, and a splice test asserting that editing one line of a comment-heavy map changes exactly one line. Verified: 1272 tests pass. Style adds no new diagnostic categories; IMPORTS moved 115 to 116 on a file whose using layout copies DiagramFileRouter.cs, which reports the same diagnostic from the same .editorconfig self-contradiction. Observation flagged not acted on: C4Document, WardleyDocument and the planned PipelineDocument are three near-identical classes containing nothing format-specific, and by the third copy the "reused as shape, not as code" decision is worth revisiting - but that would be a core change, which Requirement 12.5 says to report rather than take.
