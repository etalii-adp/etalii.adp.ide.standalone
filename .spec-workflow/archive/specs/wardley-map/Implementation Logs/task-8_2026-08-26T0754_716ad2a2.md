# Implementation Log: Task 8

**Summary:** WardleyEvolution: the four evolution stages, their three boundaries, and StageOf. The boundaries are not published in the OnlineWardleyMaps DSL documentation, so they are expressed AS their derivation rather than as literals - the reference renderer's own EvoOffsets (custom 3.5, product 8, commodity 14) each divided by an axis width of 20, giving 0.175, 0.400 and 0.700. The tests pin both halves deliberately: one asserts the division, the other asserts the resulting values, because either alone would let someone "simplify" the other into something wrong. Stage labels carry the notation's own parentheticals - "Product (+rental)", "Commodity (+utility)" - since "Product" alone is a different claim about the stage. StageOf clamps rather than throwing for a maturity outside 0..1: that is a document error Requirement 14.3 reports, and Requirement 3.5 says the rest of the map still renders, so a bad coordinate must not take the reader down with it. A value exactly on a boundary belongs to the stage it starts, so 0.4 is Product rather than Custom Built, and the theory tests each boundary exactly and just below it because "which side of the line" is the only interesting question this function answers. There is also a property test sweeping 0..1 in 0.001 steps asserting that whatever StageOf returns, the value sits inside that stage's own declared range - which catches a boundary edited in one place but not the other. This is the ONLY copy of these numbers in the repository: the client is sent Stages as a map-level element and draws the bands it is told about, per the design's "the evolution constants are sent as data, not compiled into both sides", so there is no second copy to drift. 15 tests. Verified: 1291 tests pass.
