# Implementation Log: Task 4

**Summary:** `background` - the coordinate-space backdrop wardley draws twenty-one lines for (Requirement 3.3). Four kinds, the design's own list: bands (a labelled slab per entry of a model collection), axes (a line with end labels and a rotated title), gridlines, and regions bound to a collection. Wardley's whole background is the test - four stage bands with boundaries and labels, two axes with the rotated "Value chain" title and its Visible/Invisible ends, and the attitude regions.

Coordinates are FRACTIONS OF THE EXTENT rather than canvas units, because the library cannot know a module's own scale - wardley thinks in a 0..1 evolution/value space. It is also why wardley's stage.start/stage.end drop straight in: they are already 0..1.

Per-item paths root at the ITEM, matching labels' `each` from task 2. An author who had to remember that labels.each roots at the item while bands.each roots at the payload would get it wrong, and would get it wrong SILENTLY, because a mis-rooted path resolves to nothing rather than failing. That consistency cost two new exports on the binding rather than a special case in the background.

TWO FINDINGS, BOTH FLAGGED RATHER THAN ABSORBED.

FIRST: DiagramBackgroundRef IS A THIRD FUNCTION-VALUED ESCAPE HATCH AND REQUIREMENT 2.9 DOES NOT NAME IT. 2.9 requires CustomShapeRef and CustomRouteRef to become unreachable from a module client. The background ref is the same thing for the backdrop - a module-supplied `render` the library calls - and it is used by exactly the two modules this addition exists for. It stays reachable until wardley-map and sparql migrate, because removing a contract two unmigrated modules still use would break them; the declared form sits beside it as a union, so existing modules keep working and migrated ones pass data. Flagged in the type's own doc-comment so a reader meets it there. Whether 2.9 should have named it is the architect's call, not mine.

SECOND, AND THE ONE I WANT RULED ON: TIMELINE'S RULER IS NOT A BACKGROUND. The task names it as the second instance that makes this a category rather than a special case. Read, it is view-fixed HTML chrome in a file of its own - a <div> of <span>s absolutely positioned over the scrolling surface so it never scrolls vertically out of sight, with tick positions in PIXELS derived from the viewport and a label ladder chosen per zoom by ticksFor(startSeconds, endSeconds, widthPx). Its own doc-comment says "chrome fixed to the view, not to the diagram". A canvas-space backdrop in extent fractions cannot express it, and stretching this vocabulary until it could would make it able to express anything - which is the failure mode the design itself names for decorations. It looks like task 7's chrome rather than task 4's background. I have built the wardley case, which is real and closes the measured 21-line gap, and reported this rather than papering over it.

Sabotages: drawing the boundary on every band including the outermost, and losing the rotation on a vertical axis title. Each reddens only its own fact. All 1114 pre-existing client tests pass unchanged; 1173 across 115 files, typecheck zero. Worktree commit on claude/ddm.
