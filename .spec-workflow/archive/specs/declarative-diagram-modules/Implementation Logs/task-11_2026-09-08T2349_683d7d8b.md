# Implementation Log: Task 11

**Summary:** The five single-label modules, each its own landing, each with its existing tests passing unchanged (Requirements 9.3, 9.4, 8.1, 8.2).

dotnet-dependency-graph, timeline, c4, azure-pipeline, mindmap. Sixteen custom shapes across the tree became six; every one of those five modules now declares what it used to draw.

THE MIGRATIONS FOUND TWELVE MORE GAPS THAN THE TABLE DID, and that is the headline rather than the footnote. The table reads what an element DRAWS. A migration meets everything that was ATTACHED to the drawing: the double-click handler, the accessible name, the test ids the module's own suite reads, the editor over one line of a card, where a class lands. None of that is visible in a row-by-row reading of twenty-eight renderers, and every one of them would have shipped as a silent regression.

G33 IS THE ONE WORTH READING TWICE, because it says a ruling I made was half wrong. The sufficiency table ruled on mindmap's drag preview without proof and said so at the time - "verified when mindmap migrates, and if it fails there the failure is the design's". It failed there. The candidate parent changes every frame of a drag, so no payload can carry it and no fold can compute it; the library is the only thing that knows where the drag is. The seam was in the right place - the DECISION is still the module's `onElementMoved` - and the drawing is now something the library computes, subscribing to the drag exactly as the connect preview does, so a drag frame re-renders one component and no elements.

G23 IS THE ONE THAT WOULD HAVE HURT SILENTLY. Three canvases set role, tabIndex and aria-label on the element they render. Migrating them without a declaration for it would have dropped those elements out of the tab order and off the accessibility tree, and no test in this repository would have said a word.

THREE SABOTAGES FOUND NOTHING, WHICH IS THREE FINDINGS. dependency-graph's suite does not cover edge attachment at all (its custom route picks its own anchors from the endpoint bounds); c4's does not cover where its three lines sit; and timeline's hint test asserts toContain("row 1"), which an unrounded "row 1.03333" satisfies - a vacuity that was already there and that the migration made reachable. All three now have guards, and each was seen to fail.

FIFTEEN SABOTAGES IN ALL across the five modules, plus the library guards beside them. The module suites grew 19->23 and 42->43; the client suite went 1239 -> 1250 with nothing rewritten to accommodate a migration.

A PROCESS FAILURE OF MY OWN, recorded because it matters more than the code. I landed c4 while its format gate's log was EMPTY - I grepped for FORMAT_EXIT, saw no line, and read that as fine. It is the exact failure CLAUDE.md names: a grep that prints nothing prints the same thing whether the gate passed or never ran. I re-ran gate 3 against the landed tree immediately (it exits zero, so the landing is sound) and changed the habit: every gate is now read as "does the marker EXIST", and `dotnet format` is never chained ahead of `dotnet test` in one backgrounded shell, which is what was truncating the log.

All four gates green on the merged tree for every one of the five landings, and each module's code verified onto develop with merge-base --is-ancestor.
