# Implementation Log: Task 9

**Summary:** The translation table, and the nineteen central extensions it forced (Requirements 4.1-4.4, 1.5, 3.5).

sufficiency.md: twenty-eight rows, one per CustomShapeRef declaration, read out of each canvas rather than from memory. Both dimensions verified by DIFF against the code rather than by eye - the 28 shape names match exactly, and so do the per-module counts across 13 modules (rdf has four canvases for its four readings). A count I had added by hand would have been the third wrong number in a week.

WHAT THE TABLE FOUND, AND WHY RE-READING WOULD NOT HAVE. Nineteen gaps, and the largest is the one nothing else would have surfaced: NO BUILT-IN SHAPE HAD A CLASS HOOK AT ALL. Every one hard-coded `library-shape`, so all twenty-eight rows would have migrated to the right geometry in the library's colours - no kind colour, no unresolved dash, no selection ring. A vocabulary that draws the right shapes in the wrong colours has not replaced a renderer, and eight green suites said nothing about it. The second largest: a condition could read the model and nothing else, while twenty-three of the twenty-eight rows style on selected, dragging or connectTarget.

THE PROCEDURE WAS FOLLOWED AS WRITTEN, WHICH IS THE POINT OF HAVING FIXED IT IN ADVANCE. Every gap recorded with its module and its need; every one extended CENTRALLY, in the library, for every module; the table then re-checked with the closure named per row. No module is marked an exception, nothing was added speculatively, and each entry names the row that justifies it.

Fourteen of the nineteen are one property on an existing type. Not one needed a fifth feature beside labels, decorations, background and actions - which is the design being right, and worth recording as plainly as the class hook was worth recording as wrong.

TWO ANSWERS ARE RULINGS RATHER THAN MECHANISMS, AND SAY SO IN THOSE WORDS. Mindmap's drag preview needs a model query at drag time, which no binding should express: the decision stays an event handler - the permitted carve-out - and the drawing becomes decorations conditioned on a field the fold sets. It is verified when mindmap migrates, not now, and if it fails there the failure is the design's rather than mindmap's. The problem mark stops at a boundary this specification does not own: the declaration says where a mark goes and what colours it, the module's model still says what a problem is.

ONE DEFECT FOUND BY WRITING A GUARD, NOT BY REVIEW. Number(null) is 0, so a missing count read as "0 jobs" and a missing instant as 1 Jan 1970 - data where there was none, breaking the rule the whole resolver rests on. Fixed with numberOfValue.

NINE SABOTAGES, each reddening only its own guard: state dropped from the root; an empty collection joined to a blank line; parts joined without filtering; plus applied before times; the zero-for-absent regression; declared classes dropped from the shape; a shape selection always taking its fallback; the element tooltip never drawn; alignment ignored; every column reading the first item; the modulo's sign left uncorrected; a bound decoration class dropped; the view scale left unclamped.

The unstyled-class guard also fired for real, on library-shape-inner, and was resolved through its own contract - an exemption with a reason, since that ring is painted by the same inline style as the ellipse it sits in.

All four gates green on the merged tree and the code verified onto develop with merge-base --is-ancestor: 119 files, 1237 client tests, typecheck zero, format zero, 5006 backend tests with none failed.
