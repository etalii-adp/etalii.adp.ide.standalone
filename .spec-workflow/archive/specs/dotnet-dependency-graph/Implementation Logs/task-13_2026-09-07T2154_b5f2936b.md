**Summary:** SCALE, measured against EtAlii.Adp.slnx rather than asserted. THE MEASUREMENT: 104 projects, 17 packages, 106 watched files, derived in 51-58ms. The requirements estimated roughly ninety projects (thirty backend plus sixty-one modules); the real figure is 104, so the estimate was close, and speed was never the question at this size.

READABILITY WAS. The first run's layer distribution was 1/3/7/4/3/2/4/66/14 - sixty-six diagram modules share one depth, because each references the same core and nothing references them. Stacked, that layer stood 5,850 units tall against a 3,080-unit-wide diagram: a column no screen shows at a readable zoom, which is precisely the unreadable hairball the non-functional requirement names. THE ANSWER IS A WRAP, NOT A LIMIT: the task offered grouping, filtering or a stated limit, and a limit hides part of the graph - a derived diagram that silently shows some of its subject is worse than one that is awkward to read. Wrapping a layer at twelve leaves the same 104 projects drawn and measures 5,280 x 1,440: a block rather than a ribbon, nothing hidden. LayerWrapAt's doc-comment carries the measurement so the constant is traceable to the fact that produced it.

A SECOND AND MORE SERIOUS FINDING, which only measuring produced. The first run reported two failures naming ..\..\diagrams\*\backend\*\*.csproj: this repository's host project picks up every diagram and editor module with a WILDCARD ProjectReference, MSBuild expands it, and the reader did not - it took the pattern as a literal path. The graph was not wrong so much as quietly missing most of its subject, and the two failures it did report were noise nobody could act on. Expanding wildcards segment by segment (so a * at any depth works - that pattern has three) took the graph from 349 edges and 2 failures to 427 edges and ZERO: seventy-eight real dependencies previously undrawn. An Exclude beside a wildcard is deliberately still not applied and the readme says so, because reading what a project declares rather than evaluating it is the line this reader holds and a half-evaluated pattern would be a worse answer than honest over-inclusion.

Both mechanisms seen to FAIL first. The wrap guard is paired with a second proving a wrapped layer does not draw over the layer after it - wrapping only helps if the extra columns push the next layer along, and without that the fix trades a tall ribbon for boxes on top of each other.

The probe used to measure was untracked and deleted after the run; its numbers are here and in the layout's own doc-comment.
