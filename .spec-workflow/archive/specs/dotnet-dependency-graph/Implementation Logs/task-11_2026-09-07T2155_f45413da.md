# Implementation Log: Task 11

**Summary:** Examples (Requirements 8.1-8.3). A purpose-built four-project solution, pipeline-toolkit, under examples/example 1/, replicated into src/examples/diagrams/dotnet-dependency-graph/ per structure.md. PURPOSE-BUILT RATHER THAN VENDORED, so no third-party licence question arises at all - nothing under that folder came from anywhere else, which is why Requirement 8.3's share-alike rules have nothing to bite on here.

It is small enough to read in one screen and deliberately not simple: bare PackageReference lines with a Directory.Packages.props (central package management, the ordinary case), Serilog pinned to 3.1.1 in the test project against 4.4.0 centrally so a VERSION CONFLICT is visible, a multi-targeted project whose frameworks include netstandard2.0 which names no .NET version, a dependency chain deep enough for the layered layout to have something to say, and .slnx Folder elements holding File entries beside Project ones - the shape that makes a naive reader turn Directory.Packages.props into a node. Its readme records what the corpus does NOT demonstrate: no classic .sln (none exists in this repository either), no unresolvable reference, no transitive packages, no descriptions without a local restore, and not a scale subject. EtAlii.Adp.slnx is named as the scale subject and deliberately NOT copied in, because it is already here and a stale copy would be worse than none.

THREE OF THE REPOSITORY'S GUARDS FIRED AND ALL THREE WERE RIGHT. (1) WorkspaceLock: the new client package.json joined the workspaces without package-lock.json being regenerated, which would have made npm ci refuse to install - lock regenerated. (2) ShapeOfFileAccess: SolutionReader read with a raw File.ReadAllText, which opens at FileShare.Read and loses to a concurrent save, so a solution being written by an IDE at the moment a diagram opened would have read as unreadable - now SharedDocumentReader, like every other module. (3) ExampleRegistration: the host REFUSES TO START when a type declares a document extension and registers no IDiagramDocumentFactory, and that single exception cascaded through 644 of 909 integration tests. The third is a design-level collision rather than an oversight and is routed separately in its own right; a provisional DotNetSolutionDocumentFactory unblocks the tree and documents the whole chain.

Worth recording about how those were found: docs/creating-a-diagram-module.md already names all three touch points, the factory one in bold ("Mandatory once you declare an extension - startup fails, naming your type"). I found them by running guards rather than by reading the guide the specification's own Requirement 1.4 points at. Worktree commit 6f636bd1 on claude/ddg.
