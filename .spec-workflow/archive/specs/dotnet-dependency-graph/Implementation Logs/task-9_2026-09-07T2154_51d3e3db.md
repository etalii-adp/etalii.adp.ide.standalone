# Implementation Log: Task 9

**Summary:** Refresh, automatic and explicit (Requirements 7.1-7.4). SolutionWatcher watches exactly what the graph was derived from, as DependencyGraphStore.WatchedFiles reports it: the solution, every project file it resolved, and every Directory.Packages.props above them - 106 files for this repository's own solution. A watcher over only the solution misses a reference added to a project; one over only project files misses a version bump, which under central package management lands in a props file and in no .csproj at all. One FileSystemWatcher per directory rather than per file, filtered per file: thirty projects would otherwise open thirty handles for what three directories cover. Changes settle before reporting, because a build or restore rewrites many files at once and a graph rebuilt per event would rebuild dozens of times for one logical change.

Explicit refresh exists for a reason the cache-only decision created, and this is where that decision reaches past the property it was about: a package description becomes available after a restore writes into the machine's NuGet cache, which is not a watched file and not in the workspace at all. Without an explicit refresh a user who restored a package could not make its description appear short of reopening the diagram.

THE PAIRING IS THE TEST THAT MATTERS: a change to a file the graph never read, written into the very directory being watched, must NOT wake it. Without that, the positive test passes for a watcher firing on literally anything - including this module's own .adp layout writes, which would make every drag trigger a rebuild. Both mechanisms seen to fail first (filter disabled, settling removed), plus a disposal test since a watcher outliving its session would push refreshes into a disposed connection.

The session's own tests DECLINE watching and say why: a test asserting a refresh through a real FileSystemWatcher would be asserting the file system's timing - settle delay, platform event coalescing, runner scheduling - rather than this module's behaviour. Refresh() is called directly, which is exactly what the watcher calls, and the watcher's wiring is tested apart, waiting on signals rather than sleeping fixed times. Requirements 7.2 and 7.3 are proven in the session's integration tests: a solution that gains a project keeps the authored position of an untouched one, and a removed project's element disappears.
