**Summary:** Documentation (Requirements 1.4, 7.4). Three documents, and the interesting one is the module readme rather than the catalog row.

docs/diagrams.md: the dotnet/dependency-graph row moved into the implemented section with the state icon and the origin tag, per the catalog rule.

src/diagrams/dotnet-dependency-graph/readme.md - THE FIRST MODULE-LEVEL README IN THE TREE, and written because this type has a failure mode the authored types do not. In a hand-drawn diagram a missing edge is a thing the author did not draw. IN A DERIVED ONE IT IS INDISTINGUISHABLE FROM A DEPENDENCY THAT DOES NOT EXIST, and the reader has no way to tell which they are looking at. So the readme states what the readers DO resolve (both target-framework forms, central package management's upward nearest-wins walk, a version as attribute or child element, wildcard ProjectReference expansion) and, in the same list and the same tone, what they DELIBERATELY DO NOT (MSBuild conditions, Import elements, properties inside a version or include, an Exclude beside a wildcard Include, transitive packages). Each carries why. The limits are written down rather than left for a reader to infer from a gap - that sentence is the point of the document.

It also records the two decisions a user would otherwise have to reverse-engineer from behaviour: this type writes exactly one thing, the layout: block of its own .adp registration, and never a .csproj/.sln/.slnx; and package descriptions come from the local NuGet cache's .nuspec and nowhere else, no feed, no network - with the cost stated plainly, that a package never restored on this machine shows no description, which is never an error and never a wait.

docs/creating-a-diagram-module.md: left alone deliberately, and I checked rather than assumed. The refresh rule asks whether a change MOVED a touch point named there. This module moved none - it consumed them, which is the guide working. What it did surface is that the guide already named all three guards that fired during task 11, the IDiagramDocumentFactory one in bold, and I found them by running gates instead of by reading the guide the specification's own Requirement 1.4 points at. That is a fact about the reader, not a gap in the document, and inventing an edit to it would have been the wrong repair.
