Three declarations in Diagram.cs carry decisions rather than defaults, each recorded in its own doc-comment. (1) The type declares a document sibling rather than ansible's DiagramSubject.Folder, per the design's departure: a folder subject cannot say which solution when a folder holds two. (2) .slnx is declared as AlternateExtension of .sln - the DiagramDefinition field that exists for exactly "a second serialization of the same format", whose documented behaviour is that a body carrying it registers with an explicit body: header, which is precisely the design's binding. (3) SharedExtension: true, which the design did not name and which follows from its own stated intent: a shared extension is never routed from a bare body, so a solution becomes a diagram only when the user says so through Add. Without it every .sln and .slnx in a workspace would be claimed on sight, which contradicts Requirement 2.3's "never inferred". Flagged here as an implementation reading of design intent rather than a design instruction, so it can be challenged cheaply.

Seven tests. Six restate the definition against the catalog and the design's decisions. The seventh does not: DiagramDefinitionDiscovery drops a malformed definition at the cost of one log warning, so a module that compiles green can still be invisible to the host - it asserts the definition survives an actual discovery scan. That guard was seen to FAIL first, against the exact silent-drop pairing (a folder subject declared beside the extension).
