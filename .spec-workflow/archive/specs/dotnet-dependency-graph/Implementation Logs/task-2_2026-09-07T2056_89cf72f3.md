# Implementation Log: Task 2

**Summary:** SolutionReader plus its reading model (SolutionProject, SolutionFailure, SolutionReading under _Model/), reading both serializations (Requirements 2.1, 2.2, 2.4). One fixture pair - Both.sln and Both.slnx - describes the SAME three projects (one at the root, one nested, one absent), so the formats are asserted to agree rather than each asserted on its own terms; the theories run identically over both. Nothing is fatal and nothing is silent: an absent, unreadable or unparseable solution yields no projects and a reason, and a project the solution names but which is not on disk is omitted and named in the failures, so the diagram opens with what resolved.

TWO SHAPES THE DESIGN DID NOT NAME, both found by writing the fixtures rather than by reading about them, and this is the answer to Architect 1's standing question about shapes task 2's tests did not anticipate. (1) A classic .sln writes SOLUTION FOLDERS as Project(...) lines whose second field is a folder NAME, not a path, distinguished only by the type GUID 2150E333-8FDC-42A3-9474-1A3956D46DE8. A reader taking every such line at face value emits one graph node per solution folder and then reports each as a missing project file - so the problems panel fills with findings no user can act on, and the graph gains nodes that are not projects. Handled by rejecting that GUID; guarded by a test. (2) A .slnx <Folder> carries <File> entries as well as <Project> ones - this repository files its .editorconfig, Directory.Build.props and Directory.Packages.props exactly that way - so a reader matching on the Path attribute alone would make project nodes of them. Handled by matching the element name; guarded by a test. Neither shape needed a design decision, so both are reported rather than routed as questions.

A third fact worth recording: there is NO .sln anywhere in this repository - only EtAlii.Adp.slnx - so classic-format support is exercised by fixture alone and has no live subject here. The relative path a project carries is forward-slashed on every platform, deliberately, because task 4 builds the element id from it and an id differing by separator would lose a stored position between platforms. Both mechanisms seen to FAIL first: with the folder-GUID check disabled and the separator left native, five of sixteen tests went red. 16/16 green after restoring. Worktree commit 72824123 on claude/ddg; task left [-] until it is on develop.
