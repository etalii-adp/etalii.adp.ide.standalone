# Implementation Log: Task 1

**Summary:** The release job now tags the commit it built. One file, four changes plus a verification step, merged to develop as a95c3b51 with all four gates zero on the merged tree (dotnet test 4,504 tests 0 failed and no "Zero tests ran" line, dotnet format style, npm test 89 files 859 tests, npm run typecheck).

THE DEFECT. gh release create carried no --target, so gh resolved the tag against the repository's DEFAULT BRANCH at API time rather than against github.sha. On a quiet repository the tag is right by luck; on a busy one it lands wherever develop has got to. Evidence at the time of the fix: v0.1.461-alpha, v0.1.465-alpha and v0.1.476-alpha all on f5a755c1, and v0.1.469-alpha and v0.1.481-alpha both on 8dfb7f64 - two commits carrying five tags between them, when one commit has exactly one Nerdbank height. The push that immediately preceded this fix minted v0.1.657-alpha on c76ad2f9 CORRECTLY, which is the mechanism confirming itself: that commit happened to be the branch tip when the API call ran.

THE FOUR CHANGES. (1) --target "${{ github.sha }}" on gh release create. (2) The refusal step asks two questions instead of one: the existing version-string check stays, and a second check looks for github.sha anywhere in git ls-remote --tags output. A taken version string was never the only way to republish; the same commit under a fresh number is the way that got past it five times. (3) A top-level concurrency group keyed on github.ref with cancel-in-progress FALSE - deliberately, because a run cancelled between gh release create and its asset upload leaves a tag with no ZIP behind it, which is worse than a queued run. (4) A "Skip a superseded commit" step comparing github.sha against git ls-remote origin refs/heads/develop; when they differ it emits a ::notice::, sets an output, and every publishing step is gated on it with an if:. The run stays GREEN, because being overtaken is not a failure and a red run there would teach everyone to ignore red runs.

THE VERIFICATION STEP. After publishing, the job re-reads the tag from the remote and fails loudly if it does not point at github.sha. That turns two of the four places in tests.md's "one build, one number, four places" into something the pipeline enforces on every release - the tag's commit and the version the assemblies carry. The two that still need a person are the ZIP's file name and the login line inside the running app, and the workflow comment says so where the step is.

THE TAG-SHAPE ASSUMPTION, CONFIRMED RATHER THAN INHERITED. The commit-level guard matches the sha anywhere in the ls-remote listing rather than dereferencing a named ref, because git ls-remote --tags prints the peeled refs/tags/x^{} entry beside an annotated tag. All seven tags on origin were checked with git cat-file -t and every one resolves straight to "commit" - lightweight - so a plain comparison works today. The output form covers both shapes anyway: a guard that only works for one tag shape would pass on precisely the case it exists to catch, and would do it silently.

THE GUARD EXERCISED, NOT ASSUMED. The exact expression was run locally against a released sha (99796eba, which printed its v0.1.402-alpha line) and against an unreleased one (b2553085, which printed nothing). A workflow cannot be unit-tested here and the repository is private, so its runs are unreadable from a development machine - no gh, no token, and the unauthenticated API answers Not Found for the Actions endpoints. Exercising the expressions against known shas is the available proof.

A BUG THIS WORK INTRODUCED AND CAUGHT. Both jobs have a step named "Install client dependencies". A single-occurrence string replacement gated the GATES job's copy on steps.tip.outputs.publish - an output that job does not have - which would have skipped npm ci and left the two client gates running against no dependencies. Found by parsing the YAML and printing every step with its if: rather than by reading the diff, and repaired by anchoring the edit after the tip-check marker. The lesson generalises: in a two-job workflow with mirrored step names, edit by position rather than by name.

BEHAVIOUR CHANGE, STATED IN THE FILE. A burst of five pushes now produces one release rather than five. An intermediate commit gets no release of its own; pushing it alone is how to give it one.
