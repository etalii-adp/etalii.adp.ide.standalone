# Tasks Document

**Group 1 is landable and mergeable on its own, before another line of this spec is written.** It is three edits and one added step in `.github/workflows/build.yml` — no C#, no TypeScript, no contract, nothing generated. 183 commits are unpushed behind it and every push mints another misattributed tag, so it should be handed to the user as a one-item change rather than as a spec. Nothing in groups 2, 3 or 4 is a prerequisite for it, and it is a prerequisite for none of them.

**Worktree.** `.claude/worktrees/cbh` — short, because a long worktree name pushes the deepest project paths past `MAX_PATH` and the symptom is `dotnet test` reporting `Zero tests ran` rather than failing the build. Set `MSBUILDDISABLENODEREUSE=1` and `DOTNET_CLI_USE_MSBUILD_SERVER=0` before gating. Capture every gate's exit code **into a variable before any pipe**: in a pipeline `$?` is the last command's status, so `dotnet test … | tail` reports `tail`'s success and a crashed or zero-test run reads as green.

**Specification documents are not worktree work.** This file, its approvals, its snapshots and its implementation logs are written and committed on `develop` in the main checkout with `git -C C:\git\EtAlii.Adp` and an explicit pathspec — the dashboard reads `.spec-workflow/` from there and nowhere else. Code is worktree work; documents are not.

**Identity, per commit and never per checkout.** `git -c user.name="agent-N-task" commit …`. Do **not** run `git config user.name` in the main checkout: there is one value and every session shares it, so per-task identities race and the last writer wins — that has already misattributed two commits today, one of them this spec's own design.

**Merging.** Merge through a scratch worktree, never in place. `git merge` builds its tree from the index, so a foreign staged file blocks it and its failure path dangles other sessions' uncommitted work — 26 paths across three sessions were lost that way today. Create `.claude/worktrees/mrg` at the develop tip, `git merge --no-ff` your branch **there**, run the four gates **there** on the actually-merged tree, then `git merge --ff-only` into the main checkout: a fast-forward writes no tree from the index and succeeds with foreign files staged, leaving them untouched. Waiting for a clean index is not the alternative — one staged file sat for over two hours today.

## Group 1 — the release job (landable alone, and first)

- [ ] 1. The release job names the commit it built
  - File: `.github/workflows/build.yml` (modify)
  - Four changes in one file, from the design's Piece 1: **(a)** add `--target "${{ github.sha }}"` to `gh release create` at `:154`, which is the whole of the misattribution defect; **(b)** extend the refusal step at `:103-108` with a second question — does any existing tag already point at `${{ github.sha }}` — keeping the version-string refusal beside it; **(c)** add a top-level `concurrency: { group: release-${{ github.ref }}, cancel-in-progress: false }`, false deliberately, because a run cancelled between `gh release create` and its asset upload leaves a tag with no ZIP; **(d)** add a superseded-commit step that compares `github.sha` against `git ls-remote origin refs/heads/develop`, emits a `::notice::` and skips the publishing steps via an `if:` when they differ — leaving the run **green**, since being overtaken is not an error and a red run there teaches everyone to ignore red runs.
  - Add the **post-publish verification** the design specifies: re-read the tag with `git ls-remote` and fail loudly if it does not point at `${{ github.sha }}`. This is what turns the check from a promise into an enforcement.
  - **The tag shape is measured, not assumed.** `git cat-file -t` resolves `v0.1.402-alpha` and `v0.1.476-alpha` straight to `commit`, so the tags `gh release create` produces today are **lightweight** and a plain sha comparison works. Keep the guard's output form covering the peeled `refs/tags/x^{}` entry anyway, and **re-confirm with `git cat-file -t` before trusting it**: if `gh` ever produces an annotated tag, `refs/tags/x` names a tag object rather than a commit and a naive comparison would miss precisely the case the guard exists to catch.
  - **State the behaviour change in the workflow's own comments**: a burst of five pushes now produces one release rather than five, because a superseded commit is skipped. That is Requirement 3.2 and it is deliberate.
  - Do **not** touch the four misattributed tags in this task. `v0.1.402-alpha` is correct and stays; the recommendation for the other four is **delete all four** — days-old alphas whose misattribution cannot be explained away, and a tag pointing at the wrong source is worse than a missing one because it looks like an answer. The decision is the user's and it does not block this fix.
