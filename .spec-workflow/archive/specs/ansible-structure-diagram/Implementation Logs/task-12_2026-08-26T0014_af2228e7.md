# Implementation Log: Task 12

**Summary:** AnsibleProjectStore + IAnsibleProjectStore + AnsibleWatchedFolder + AnsibleProjectChangedEventArgs: one AnsibleProject per registered folder, re-read when the tree changes. Watcher copies TrackedProblemRoot's shape exactly - IncludeSubdirectories, FileName|DirectoryName|LastWrite|Size, a settle timer that restarts until a burst settles, and every handler guarded because they run on the watcher's own thread where an unhandled exception kills the process. No save method and no code path that opens a file for writing; a test asserts the interface has no Save/Write/Update method so adding one says so out loud. TWO DECISIONS BEYOND THE TASK TEXT, both recorded in the code. (1) I ADDED Acquire(folder) alongside GetOrLoad/Get/Release. The task named only the three, but with a single count incremented by GetOrLoad there is no correct answer: the context source resolver and anything else that merely looks would inflate the count and prevent teardown, while making Release unconditional means a second connection closing tears the watcher out from under the first, whose diagram then goes QUIETLY stale - the exact failure this diagram type exists to prevent. So reading (GetOrLoad/Get) and lifetime (Acquire/Release) are separate, and ReleasingOneOfTwoClaims_KeepsTheFolderWatched pins it. (2) A settled burst re-reads the WHOLE folder rather than surgically re-reading changed files, which the task text and the design's AnsibleProjectReader.Reread sketch both called for. An incremental path would be a second way to build a model, able to disagree with the first, and that failure mode is a diagram that is subtly wrong rather than obviously broken. The burst timer already collapses a multi-file save into one re-read and the walk is milliseconds. The class comment names AnsibleProjectReader - memoizing per-file parses behind the same walk - as the place to optimise if a project ever appears where that is not true, rather than a divergent path in the store. OnSettled re-reads BEFORE raising Changed, so a listener that asks the store during the event is not handed the project the event exists to replace; there is a test for that. One test-authoring mistake: my first change-detection test wrote to roles/common/meta/main.yml, which does not exist - common is deliberately the fixture role with no meta at all, as its own reader test asserts. Switched to editing nginx's meta. Verified: build 0 errors; module 75/75, run twice since watcher tests are flake-prone; committed fixture trees confirmed untouched by git status. Phase D is complete.
