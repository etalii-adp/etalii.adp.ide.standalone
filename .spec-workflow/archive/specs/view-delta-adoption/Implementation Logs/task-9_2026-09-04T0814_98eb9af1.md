# Implementation Log: Task 9

**Summary:** rdf implements the loop across all four readings, and its truncation is re-evaluated.

**Four readings, not three.** `shacl-diagram` merged after the tasks document was approved, so the family is `RdfSession`, `OwlSession`, `SkosSession` and `ShaclSession` plus four canvases. All four now answer a viewport change with deltas; all four client canvases report.

**The central design decision: the whole document is projected and laid out whatever the viewport says, and only then filtered.** Every reading's layout packs by what is in it — bands, grids, a walked hierarchy — so a layout computed over the *visible* set would repack as the reader panned and the diagram would crawl under them. It is also the only way a resource the reader pans to can have a position at all. `PanningDoesNotMoveTheNodesItBringsIntoView` pins it, and the projection plus layout is cached per session and dropped only on a document change, so a pan costs a filter rather than a re-projection.

**Requirement 5.4, and the trap inside it.** The budget survives as a floor on the *in-view* set: only a view holding more than 1,000 nodes is cut. But the counts handed on are still the **document's**, and that is deliberate — `RdfSelection.IsTruncated` decides both the banner and the read-only refusal from the document alone, with no viewport to consult. A banner derived from the view would have contradicted it: a file could be read-only with nothing on screen saying why, or claim truncation while every edit was allowed. **Reach improves; what a document may do is unchanged.** `ADocumentOverTheBudget_KeepsItsBannerAndItsRefusal` guards that pair.

**The payoff test.** `PanningReachesResourcesTheBudgetDiscarded` builds a 1,200-resource document, asserts the opening view still draws exactly the budget, then reports a viewport over the far end of the layout and asserts resources arrive that the baseline never sent. Before this, resource 1,001 was unreachable however far anyone panned, because the cut was by document order and panning changed nothing about which thousand the backend had picked.

**Two findings.**

1. **A test assertion of mine was vacuous and sabotage caught it.** The client test first asserted only that a zoom produced *another* report. Keying the view on `{x, y, 1, 1}` — dropping zoom entirely — still passed, because this canvas's zoom moves the origin as well and re-fires the report regardless. The assertion now compares the reported rectangle's *span*, which no origin change can fake, and the conversion sabotage fails it.
2. **rdf's two new imports tipped over an unrelated module's test.** `ansible-structure/client/register.test.ts` is the only test that imports the shell's canvas registry, and the registry globs every module — so that one test imports every canvas in the repository, cold, in a fresh jsdom worker. That cost had quietly reached vitest's 5000ms default. It failed in the full suite, passed alone, and reverting *only* the rdf client changes turned the suite green, which is what identified it. The budget is now stated with its reason; an undeclared one fails in a module that did not change.

**Requirement 3.6 exercised for real:** rdf hand-rolls its open loop (`createClient` directly, not `useDiagramStream`), and it adopted the shared report without touching that. Also found: the three other canvas test mocks did not supply `reportView` at all — a latent crash for the first of them to use fake timers, now fixed.

**Within-module factoring, not a shared backend helper (Requirement 4):** `RdfViewport.Admits` is one intersection test for the family's four readings, and `rdfViewport.ts` one pixels-per-unit conversion for its four canvases. Both live inside the module and nothing outside can reach them. The four sessions' `InView` methods are *not* merged — they take different node collections and differ in input, exactly the case Requirement 4.1 describes.
