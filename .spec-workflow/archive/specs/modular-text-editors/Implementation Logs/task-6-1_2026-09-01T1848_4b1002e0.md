# Implementation Log: Task 6.1

**Summary:** OpenAsTextContextActionProvider mirrors AddDiagramContextActionProvider: 'Open as text' (editor.open-as-text) offered only on files DiagramFileRouter routes as diagrams (R5.2), disabled-with-reason on an undefaulted editor conflict; 'Open with…' (editor.open-with) offered only for a legitimately shared extension with a declared default (R4.4), executing as ContextExecutionRequiresChoice listing every claimant (EditorResolver gained ClaimantsOf(path) for this - Resolve still decides who opens on activation). No synchronization code between coexisting diagram/text sessions - the disk is the tie-breaker by construction (R5.5). The wire gap the design left open was closed within the actual Non-Functional requirement ('no module opens a stream of its own' - fields and unary calls are permitted, only new streams are banned; the task-doc's 'proto diff empty' proxy was stricter than the requirement and is recorded as spec finding #10): OpenDiagramRequest gained editor_id ('' = today's diagram-first resolution; '*' = force the editor family, resolver decides; an id = the editor chosen via Open with…), which is the only way a diagram stream and a text stream of the same path can coexist on one connection. DiagramService.Open grew the forced arm and stopped registering editor sessions in the viewport registry (keyed (watch,path) - the text stream would have overwritten and then deregistered the diagram's entry). Client half: tabs are per-connection client state, so the gesture completes client-side (the context channel carries no gesture data): a textTabRequests module-level bus (same shape as dirtyTabs), ContextConnectionProvider special-cases the two action ids (open-as-text opens a tab with editorId '*' on accept; open-with remembers the file and opens the tab with the chosen option id at submit), and ResolvedTextEditorPanel (mime sentinel 'editor/*') reads the content element's own type from the stream to mount the right module's canvas - the client keeps no file-type table.
