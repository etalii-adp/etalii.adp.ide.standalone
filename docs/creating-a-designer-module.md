# Creating a designer module

How to give ADP a designer - the third family of tools, beside [diagrams](creating-a-diagram-module.md) and [editors](creating-an-editor-module.md). **No designer exists yet**: this document is the placeholder that says where one goes and what it can count on, so the first designer module starts from a prepared place rather than from a copy of a diagram module.

## What a designer is

A designer is a form-based visual layout: more than text input, and not a diagram, because nothing in it is connected. Apply the tests of [ADP terminology](https://github.com/etalii-adp/etalii.adp/blob/develop/docs/terminology.md) in order: when typing text is the main thing the user does, it is an editor; when its elements are connected, it is a diagram; when it is laid out visually and filled in, with nothing connected, it is a designer. Every tool ADP offers today is a diagram or an editor ([`docs/tools.md`](tools.md)), so a new designer is also a new row there, of kind Designer.

## What is already prepared

- **The folder**: [`src/designers`](../src/designers), beside `src/diagrams` and `src/editors`, holding only its readme.
- **Discovery and registration**: [`DesignerDefinitionDiscovery`](../src/backend/EtAlii.Adp.Designer/DesignerDefinitionDiscovery.cs) scans the application's assemblies for a static `Designer` class with a public static `Definitions` property holding [`DesignerDefinition`](../src/backend/EtAlii.Adp.Designer/_Model/DesignerDefinition.cs)s - the same scan, `ToolDefinitionScan`, that finds `Diagram` and `Editor` classes. The host runs it at startup, today finds none, and registers what it finds with [`AddDesignerDefinitions`](../src/backend/EtAlii.Adp.Designer/_Model/HostApplicationBuilder.AddDesignerDefinitions.cs): each definition's `Build` runs, and the definitions are served through [`IDesignerDefinitionCatalog`](../src/backend/EtAlii.Adp.Designer/IDesignerDefinitionCatalog.cs).
- **The definition**: a `DesignerDefinition` declares its origin (`<vendor>/<type>`), title, description, icon, the file formats a document can be created in ([`DesignerFormat`](../src/backend/EtAlii.Adp.Designer/_Model/DesignerFormat.cs): a name and an extension, chosen when the document is added) and `Build`. These live in the core project `EtAlii.Adp.Designer`, beside `EtAlii.Adp.Diagram` and `EtAlii.Adp.Editor`.
- **Routing**: [`DesignerFileRouter`](../src/backend/EtAlii.Adp.Hierarchy/DesignerFileRouter.cs) decides which files are a designer's. A designer's document is always two files, so the only thing that makes a file a designer's is a registration: an `.adp` whose first line is the designer's origin, and the body it names - by a `body:` header, or as the file of its own name in the first of the definition's formats that exists. A body is never claimed by its extension. The router is asked after the diagram family and before the editor family, in three places: the tree already carries a registration's first line as the entry's type, which is what the client keys a panel on; opening a designer's registration or body is refused by name rather than shown as text, until the family has a session to open; and project validation judges a designer's document by the rules registered for its origin, through the same `IDiagramValidator` registry diagram types use, instead of reporting an unknown diagram type.
- **Adding a document**: a designer type that declares formats and registers an [`IDesignerDocumentTemplate`](../src/backend/EtAlii.Adp.Designer/IDesignerDocumentTemplate.cs) is offered in the workspace tree's **Add…** dialog, under its vendor beside the diagram types, with one choice per format ([`DesignerAddOptions`](../src/backend/EtAlii.Adp.Hierarchy/DesignerAddOptions.cs)). Choosing one creates two files as one undoable step: the body, whose content is what the module's template returns for that format (a module with an FBL binding returns its binding's template through `TemplateWriter`), and the registration, which holds the origin and a `body:` line naming the body and nothing else. The `body:` line is always written, because a body has one of several extensions and another file of the same name must not be taken for it. Deleting either file removes the other. Nothing offers to change a document's format.
- **The session and the wire**: a module registers an [`IDesignerSessionFactory`](../src/backend/EtAlii.Adp.Designer/IDesignerSessionFactory.cs) for its origin. The host resolves a path to the designer's document and opens one [`IDesignerSession`](../src/backend/EtAlii.Adp.Designer/IDesignerSession.cs) per connection, which ends with its stream. A session speaks the table model in [`TableModel/`](../src/backend/EtAlii.Adp.Designer/TableModel): columns, views, the active view's settings, the lines of the window the client has in sight, findings, and what became of an edit. The model names no designer type. [`DesignerService`](../src/backend/EtAlii.Adp.Diagram/DesignerService.cs) carries it: `OpenTable` and `CloseTable` join and leave the tab's one stream, where the table arrives as the `table` member of `WorkspaceMessage`; `SetTableWindow`, `SetTableView` and `Edit` reach the session. Every call of [`designers.proto`](../src/api/designers.proto) is unary, and a test refuses a streaming one. An edit is answered as soon as it is accepted and its write is reported afterwards, so a session shows an edit at once and writes behind.
- **The client registry**: the shell's [`toolPanels.ts`](../src/client/src/shell/panels/toolPanels.ts) globs `{diagrams,designers,editors}/*/client/register.ts`, so a designer's `register.ts` is picked up with no shell edit, exactly as the other families' are.

## What the family will share

Read [creating a diagram module](creating-a-diagram-module.md) for the mechanism every family uses; a designer module follows it with `designers` in place of `diagrams` and `Designer` in place of `Diagram`:

- the same four folders - `backend/` (`EtAlii.Adp.Designer.<Designer>` and its `.Tests`), `api/`, `client/`, `examples/` - and the same dependency direction: a module depends on core, never the other way round;
- a static `Designer` class exposing `Definitions`, whose origin (`<vendor>/<type>`) names the designer type in its `.adp` registration's first line;
- a `client/register.ts` exporting `registrations` of `ToolPanelRegistration`, whose `Panel` mounts the table library's `TableSurface` on the table `useTableStream` holds and writes no element of its own;
- xUnit v3 test projects added to `EtAlii.Adp.slnx`, and examples seeded into the showcase under `src/examples`, in a `designers` folder beside `diagrams` and `editors`.

## What the first designer adds

The first designer is the Knowledge designer, in [`src/designers/knowledge`](../src/designers/knowledge). Its backend shows what a designer module supplies:

- [`Designer.cs`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/Designer.cs): the definition, with its origin, its formats and a `Build` that registers the module's services.
- [`definition/`](../src/designers/knowledge/definition): the specification (`knowledge.des`) and the bindings (`knowledge.fbl`), copied byte for byte from etalii-adp/etalii.adp and embedded, with `provenance.json` recording the revision and each file's sha256. A test fails when a bundled file no longer hashes to what was recorded.
- [`KnowledgeBody`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeBody.cs): a document read through `EtAlii.Adp.Specification.Fbl` with the binding its extension selects. The module has no parser and no writer of its own, which is what makes the three formats one table.
- [`KnowledgeSession`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeSession.cs): the session of one connection. It reads the file with the shared read, writes nothing on open, and watches the file with a text editor session's obligations: subscribed before the watcher is enabled, read again when events were lost, and a refused read retried.
- [`KnowledgeTableMapper`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeTableMapper.cs): the document onto the host's table model.
- [`KnowledgeViewEngine`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeViewEngine.cs): a view's lines, computed on the backend - the rows its filter lets through, in the order its sorts give, under the headings of its grouping or nested under their parents - so the client draws the window it asks for and never the whole table. Its tests check properties of the result over a table of some hundreds of rows: every row shown passes the filter and every row hidden does not, a sort is an order and is stable, and a grouping loses no row.
- [`KnowledgeRelations`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeRelations.cs): relations between knowledge files. A relation stores its target's path relative to its own file and its values as the target's row ids; what a value is called is read from the target, so renaming a row there changes no byte here. The other side of a two-way relation is a property of the target, computed and without cells, filled in from the side that holds the values each time it is shown. Making a two-way relation is one command over two files: both are planned before either is written, and its inverse restores both.
- [`KnowledgeValidator`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeValidator.cs): what the designer's own rules find in a table, one code per condition of the specification's list, each at its place and all of them every time. Reporting changes nothing: what is reported is still in the file after an edit of anything else.
- [`KnowledgeVocabulary`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeVocabulary.cs): the specification's words the module implements, written out and not read from it, so that the two can differ - and `DefinitionConformance.Tests` fails when they do, naming what is missing from the module or unknown to the definition.
- [`KnowledgeEdits`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeEdits.cs): every gesture of the table as the changes it means for the file, with what it refuses and in which words. It reads a table and writes nothing. A change of type converts each value as the conversion table of `knowledge.md` says, and a test reads that table and fails on a cell the module treats differently.
- [`KnowledgeEditCommand`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeEditCommand.cs): one edit as a command. Its handler makes the changes through the FBL runtime on a copy of the body, all of them or none, saves with the central writer, and reports the file's content from before as its inverse, so an undo is the application's undo and gives the bytes back exactly.
- [`KnowledgeProjection`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeProjection.cs): the same changes made to the model in memory. This is what lets the session show an edit at once and write it behind: it shows the projection, queues the command, and reads the file again when the write has landed. A refused write takes the edit back, and every later edit that was made on top of it. One test makes every gesture in each format and fails when what was shown before the write is not what the file holds after it.

Its client is three files, and shows the whole of what a designer module's client is:

- [`knowledgeDefinition.ts`](../src/designers/knowledge/client/knowledgeDefinition.ts): the table as declarations - each value type's name, icon, editor and comparisons, and what a property's menu offers. A test reads `knowledge.des` and fails when a name, an icon or a comparison differs from it.
- [`KnowledgePanel.tsx`](../src/designers/knowledge/client/KnowledgePanel.tsx): `useTableStream(path)` handed to `TableSurface` - the model, the count of edits not written yet, and the three handlers. The hook reports the stream's state and every refused edit to the frame the shell puts around each tool, which says *Opening…*, why a table cannot be opened and why an edit was taken back in the one appearance all tools share; the table itself says only that it is read-only or still saving. A module draws no status either. `declarativeDesignerModules.test.ts` refuses an element written in a module's client, and counts the clients it walks.
- [`register.ts`](../src/designers/knowledge/client/register.ts): the registration, matching the designer's origin.

From the explorer a knowledge file offers one action, *Add relation*, through [`KnowledgeContextActionProvider`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeContextActionProvider.cs): the table to relate to is asked for in the host's file dialog, which the provider tells to take knowledge files only and to offer this table first. It makes the relation with the same gesture and the same command an edit in the table uses, so the two cannot drift.

Two tests go through the whole host with the module deployed: [`KnowledgeDesigner.Tests`](../src/backend/EtAlii.Adp.Backend.Tests/Integration%20Tests/KnowledgeDesigner.Tests.cs) opens, edits and closes the example in each format over gRPC, and [`DesignerModuleIsolation.Tests`](../src/backend/EtAlii.Adp.Backend.Tests/Integration%20Tests/DesignerModuleIsolation.Tests.cs) fails when a core file names the module.

A module client is an npm workspace package (`designers/*/client` in [`src/package.json`](../src/package.json)); adding one means adding its entry to `src/package-lock.json` in the same change.


What a designer needs beyond the scan is decided by its specification, the way `modular-text-editors` decided the editor family's: the routing and session seams the host serves designers through (the definition and its catalog are in place), and - when ADP specifies designer types in a language - DESL, the Designer Specification Language, with the designs users create stored as DED, the Designer Definition Language. Extend this document in the same change.
