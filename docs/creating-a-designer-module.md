# Creating a designer module

How to give ADP a designer - the third family of tools, beside [diagrams](creating-a-diagram-module.md) and [editors](creating-an-editor-module.md). The first one is the Knowledge designer, in [`src/designers/knowledge`](../src/designers/knowledge); this document says where a designer goes and what it can count on, so a new designer module starts from a prepared place rather than from a copy of a diagram module.

## What a designer is

A designer is a form-based visual layout: more than text input, and not a diagram, because nothing in it is connected. Apply the tests of [ADP terminology](https://github.com/etalii-adp/etalii.adp/blob/develop/docs/terminology.md) in order: when typing text is the main thing the user does, it is an editor; when its elements are connected, it is a diagram; when it is laid out visually and filled in, with nothing connected, it is a designer. A new designer is also a new row in [`docs/tools.md`](tools.md), of kind Designer.

## What is already prepared

- **The folder**: [`src/designers`](../src/designers), beside `src/diagrams` and `src/editors`, holding only its readme.
- **Discovery and registration**: [`DesignerDefinitionDiscovery`](../src/backend/EtAlii.Adp.Designer/DesignerDefinitionDiscovery.cs) scans the application's assemblies for a static `Designer` class with a public static `Definitions` property holding [`DesignerDefinition`](../src/backend/EtAlii.Adp.Designer/_Model/DesignerDefinition.cs)s - the same scan, `ToolDefinitionScan`, that finds `Diagram` and `Editor` classes. The host runs it at startup and registers what it finds with [`AddDesignerDefinitions`](../src/backend/EtAlii.Adp.Designer/_Model/HostApplicationBuilder.AddDesignerDefinitions.cs): each definition's `Build` runs, and the definitions are served through [`IDesignerDefinitionCatalog`](../src/backend/EtAlii.Adp.Designer/IDesignerDefinitionCatalog.cs).
- **The definition**: a `DesignerDefinition` declares its origin (`<vendor>/<type>`), title, description, icon, the file formats a document can be created in ([`DesignerFormat`](../src/backend/EtAlii.Adp.Designer/_Model/DesignerFormat.cs): a name and an extension, chosen when the document is added) and `Build`. These live in the core project `EtAlii.Adp.Designer`, beside `EtAlii.Adp.Diagram` and `EtAlii.Adp.Editor`.
- **Routing**: [`DesignerFileRouter`](../src/backend/EtAlii.Adp.Hierarchy/DesignerFileRouter.cs) decides which files are a designer's. A file is a designer's by a registration: an `.adp` whose first line is the designer's origin, and the body it names - by a `body:` header, or as the file of its own name in the first of the definition's formats that exists. A designer whose definition carries a [`DesignerClaim`](../src/backend/EtAlii.Adp.Designer/_Model/DesignerClaim.cs) is also recognised by its document's envelope: a body of one of the claim's extensions whose first line the claim matches (a module answers it with its FBL binding's marker, through [`BodyClaim`](../src/backend/EtAlii.Adp.Specification.Fbl/Routing/BodyClaim.cs)) is that designer's document, with the registration of its type that names it or with none, and whatever another tool's registration says of it; that other registration is refused with the reason. Only the first line is read, up to its line break or 1,024 bytes, and kept until the file changes ([`FirstLineCache`](../src/backend/EtAlii.Adp.Hierarchy/FirstLineCache.cs)). A body is never claimed by its extension alone. The envelope is asked before every family; a registration is asked after the diagram family and before the editor family, an order decided in one place, [`ToolRouter`](../src/backend/EtAlii.Adp.Hierarchy/ToolRouter.cs), whose answer the callers go by: opening a designer's registration or body is refused by name rather than shown as text, until the family has a session to open; project validation judges a designer's document by the rules registered for its origin, through the same `IDiagramValidator` registry diagram types use, instead of reporting an unknown diagram type; the tree nests the registration under its body; and deleting either file takes the other with it, except that deleting the registration of a type whose claim creates its registration on first placement leaves the body, which opens without it. The tree also carries a registration's first line as the entry's type, which is what the client keys a panel on.
- **Adding a document**: a designer type that declares formats and registers an [`IDesignerDocumentTemplate`](../src/backend/EtAlii.Adp.Designer/IDesignerDocumentTemplate.cs) is offered in the workspace tree's **Add…** dialog, under its vendor beside the diagram types, with one choice per format ([`DesignerAddOptions`](../src/backend/EtAlii.Adp.Hierarchy/DesignerAddOptions.cs)). For a type whose claim creates its registration on first placement, choosing one writes the body alone, and a name whose file is there already is accepted when that file carries the envelope (it opens, and nothing is written) and refused, naming the line it needs, when it does not. Otherwise choosing one creates two files as one undoable step: the body, whose content is what the module's template returns for that format (a module with an FBL binding returns its binding's template through `TemplateWriter`), and the registration, which holds the origin and a `body:` line naming the body and nothing else. The `body:` line is always written, because a body has one of several extensions and another file of the same name must not be taken for it. Deleting either file removes the other. Nothing offers to change a document's format.
- **Following a rename**: a designer type whose files name other files by their path registers an [`IEntryRenameFollower`](../src/backend/EtAlii.Adp.Documents/IEntryRenameFollower.cs). The explorer's rename tells it where a file or folder was and where it is now, in the same undoable step, and tells it again the other way when the rename is undone. The Knowledge designer's [`KnowledgeTargetRename`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeTargetRename.cs) rewrites the relations that name a renamed table this way. There is no move in the explorer yet, and a registration renamed by itself is not followed.
- **The session and the wire**: a module registers an [`IDesignerSessionFactory`](../src/backend/EtAlii.Adp.Sessions/IDesignerSessionFactory.cs) for its origin, whose `Open` is handed the project as a [`ProjectRoot`](../src/backend/EtAlii.Adp/ProjectRoot.cs), the body, and the registration, which is null for a document recognised by its envelope that has none yet; the session contracts of every kind of tool are in the sessions project, `EtAlii.Adp.Sessions`, which the module references. The host resolves a path to the designer's document and opens one [`IDesignerSession`](../src/backend/EtAlii.Adp.Sessions/IDesignerSession.cs) per connection, which ends with its stream; that contract holds only what every kind shares, and a session is of the kind of the surface its specification names. A table session, [`ITableDesignerSession`](../src/backend/EtAlii.Adp.Sessions/ITableDesignerSession.cs), speaks the table model in [`TableModel/`](../src/backend/EtAlii.Adp.Designer/TableModel): columns, views, the active view's settings, the lines of the window the client has in sight, findings, and what became of an edit. A hierarchy surface session, [`IHierarchySurfaceSession`](../src/backend/EtAlii.Adp.Sessions/IHierarchySurfaceSession.cs), speaks the read model in [`HierarchySurfaceModel/`](../src/backend/EtAlii.Adp.Designer/HierarchySurfaceModel): the whole page - levels and entries with their labels, option lists, filters, notes and findings - sent on open and after every change, and what became of a gesture. Neither model names a designer type. [`DesignerService`](../src/backend/EtAlii.Adp.Workspace/DesignerService.cs) carries them: `OpenTable` and `CloseTable` join and leave the tab's one stream, where the table arrives as the `table` member of `WorkspaceMessage`, and `SetTableWindow`, `SetTableView` and `Edit` reach the session; `OpenHierarchySurface` and `CloseHierarchySurface` do the same for a page, which arrives as the `hierarchy_surface` member, and `HierarchySurfaceGesture` reaches its session. Opening a document as the other kind is refused by name. Every call of [`designers.proto`](../src/api/designers.proto) is unary, and a test refuses a streaming one. An edit is answered as soon as it is accepted and its write is reported afterwards, so a session shows an edit at once and writes behind.
- **The client registry**: the shell's [`toolPanels.ts`](../src/client/src/shell/panels/toolPanels.ts) globs `{diagrams,designers,editors}/*/client/register.ts`, so a designer's `register.ts` is picked up with no shell edit, exactly as the other families' are.

## What the family will share

Read [creating a diagram module](creating-a-diagram-module.md) for the mechanism every family uses; a designer module follows it with `designers` in place of `diagrams` and `Designer` in place of `Diagram`:

- the same four folders - `backend/` (`EtAlii.Adp.Designer.<Designer>` and its `.Tests`), `api/`, `client/`, `examples/` - and the same dependency direction: a module depends on core, never the other way round;
- a static `Designer` class exposing `Definitions`, whose origin (`<vendor>/<type>`) names the designer type in its `.adp` registration's first line;
- a `client/register.ts` exporting `registrations` of `ToolPanelRegistration`, whose `Panel` mounts the table library's `TableSurface` on the table `useTableStream` holds, or the hierarchy surface library's `HierarchySurface` on the page `useHierarchySurfaceStream` holds, and writes no element of its own;
- xUnit v3 test projects added to `EtAlii.Adp.slnx`, and examples seeded into the showcase under `src/examples`, in a `designers` folder beside `diagrams` and `editors`.

## What the first designer adds

The first designer is the Knowledge designer, in [`src/designers/knowledge`](../src/designers/knowledge). Its backend shows what a designer module supplies:

- [`Designer.cs`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/Designer.cs): the definition, with its origin, its formats and a `Build` that registers the module's services.
- [`definition/`](../src/designers/knowledge/definition): the specification (`knowledge.des`) and the bindings (`knowledge.fbl`), copied byte for byte from etalii-adp/etalii.adp and embedded, with `provenance.json` recording the revision and each file's sha256. A test fails when a bundled file no longer hashes to what was recorded.
- [`KnowledgeBody`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeBody.cs): a document read through `EtAlii.Adp.Specification.Fbl` with the binding its extension selects. The module has no parser and no writer of its own, which is what makes the three formats one table.
- [`KnowledgeSession`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeSession.cs): the session of one connection. It reads the file with the shared read, writes nothing on open, and watches the file with a text editor session's obligations: subscribed before the watcher is enabled, read again when events were lost, and a refused read retried. Inside a project whose root is watched, it hears the file through that root's one watcher (`ProjectFileEvents`) rather than a watcher of its own. Its state is kept by job: the edits shown and not yet written, and their writes one at a time, in a [`PendingEditQueue`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/PendingEditQueue.cs), whose generation makes a refused write take every later edit back with it; and what the connection looks at - its view, the rows an edit added, its search and its window - in a [`KnowledgeViewState`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeViewState.cs). Neither has a lock of its own: the session touches both with its one lock held.
- [`KnowledgeTableMapper`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeTableMapper.cs): the document onto the host's table model.
- [`KnowledgeViewEngine`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeViewEngine.cs): a view's lines, computed on the backend - the rows its filter lets through, in the order its sorts give, under the headings of its grouping or nested under their parents - so the client draws the window it asks for and never the whole table. Its tests check properties of the result over a table of some hundreds of rows: every row shown passes the filter and every row hidden does not, a sort is an order and is stable, and a grouping loses no row.
- [`KnowledgeRelations`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeRelations.cs): relations between knowledge files. A relation stores its target's path relative to its own file and its values as the target's row ids; what a value is called is read from the target, so renaming a row there changes no byte here. The other side of a two-way relation is a property of the target, computed and without cells, filled in from the side that holds the values each time it is shown. Making a two-way relation is one command over two files: both are planned before either is written, and its inverse restores both.
- [`KnowledgeValidator`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeValidator.cs): what the designer's own rules find in a table, one code per condition of the specification's list, each at its place and all of them every time. Reporting changes nothing: what is reported is still in the file after an edit of anything else.
- [`KnowledgeValueTypes`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeValueTypes.cs): the value types, one strategy each ([`KnowledgeValueType`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeValueType.cs)) - the key a value is stored under, how a filter compares it and a sort orders it, which groups a grouping by it has, how it is written, and what it becomes when its property changes type. The view engine, the edits, the calculations and the validator ask a property's strategy rather than switching on its type's name, and a name the specification does not have is a type of its own, whose values are kept and shown as text. `KnowledgeValueTypes.Tests` fails when a type of `knowledge.des` is not found by its name, or when the key a type says its values are under is not the key a cell of it has in the shipped example.
- [`KnowledgeVocabulary`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeVocabulary.cs): the specification's words the module implements, written out and not read from it, so that the two can differ - and `DefinitionConformance.Tests` fails when they do, naming what is missing from the module or unknown to the definition. The value types' words are read from `KnowledgeValueTypes`, so there is one list of them.
- [`KnowledgeEdits`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeEdits.cs): every gesture of the table as the changes it means for the file, with what it refuses and in which words. It reads a table and writes nothing. Each gesture is an entry of its table of gestures, found by its whole kind and saying itself whether it is about the view shown, so a table without views refuses exactly those; it is planned by the edits of what it changes: [`KnowledgeCellEdits`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeCellEdits.cs) a row's cells and the rows, [`KnowledgeColumnEdits`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeColumnEdits.cs) a property with its type, its relation and its options, [`KnowledgeViewEdits`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeViewEdits.cs) the views and how the view shown shows its rows, and [`KnowledgeFilterEdits`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeFilterEdits.cs) a view's filter. A new gesture is a method of one of them and an entry in the table. A change of type converts each value as the conversion table of `knowledge.md` says - each value type's strategy converting its own values - and a test reads that table and fails on a cell the module treats differently.
- [`KnowledgeEditCommand`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeEditCommand.cs): one edit as a command. Its handler makes the changes through the FBL runtime on a copy of the body, all of them or none, saves with the central writer, and reports the file's content from before as its inverse, so an undo is the application's undo and gives the bytes back exactly.
- [`KnowledgeProjection`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeProjection.cs): the same changes made to the model in memory. This is what lets the session show an edit at once and write it behind: it shows the projection, queues the command, and reads the file again when the write has landed. A refused write takes the edit back, and every later edit that was made on top of it. One test makes every gesture in each format and fails when what was shown before the write is not what the file holds after it.

Its client is three files, and shows the whole of what a designer module's client is:

- [`knowledgeDefinition.ts`](../src/designers/knowledge/client/knowledgeDefinition.ts): the table as declarations - each value type's name, icon, editor and comparisons, and what a property's menu offers. A test reads `knowledge.des` and fails when a name, an icon or a comparison differs from it.
- [`KnowledgePanel.tsx`](../src/designers/knowledge/client/KnowledgePanel.tsx): `useTableStream(path)` handed to `TableSurface` - the model, the count of edits not written yet, and the three handlers. The hook reports the stream's state and every refused edit to the frame the shell puts around each tool, which says *Opening…*, why a table cannot be opened and why an edit was taken back in the one appearance all tools share; the table itself says only that it is read-only or still saving. A module draws no status either. `declarativeDesignerModules.test.ts` refuses an element written in a module's client, and counts the clients it walks.
- [`register.ts`](../src/designers/knowledge/client/register.ts): the registration, matching the designer's origin.

From the explorer a knowledge file offers one action, *Add relation*, through [`KnowledgeContextActionProvider`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge/KnowledgeContextActionProvider.cs): the table to relate to is asked for in the host's file dialog, which the provider tells to take knowledge files only and to offer this table first. It makes the relation with the same gesture and the same command an edit in the table uses, so the two cannot drift. A relation is also a type in the table's own *New property* panel, as it is in Notion: the definition marks the kind `needsTarget`, the panel asks the session which tables there are with an `addRelation` gesture that names none, and the session answers with a list that begins `choose:` - a question, like one that begins `confirm:`, and not a refusal. The relation's limit and its other side are edited from *Edit relation* in the column's menu.

Two tests go through the whole host with the module deployed: [`KnowledgeDesigner.Tests`](../src/designers/knowledge/backend/EtAlii.Adp.Designer.Knowledge.Tests/KnowledgeDesigner.Tests.cs) opens, edits and closes the example in each format over gRPC, and [`DesignerModuleIsolation.Tests`](../src/tests/EtAlii.Adp.Modules.Tests/DesignerModuleIsolation.Tests.cs) fails when a core file names the module.

A module client is an npm workspace package (`designers/*/client` in [`src/package.json`](../src/package.json)); adding one means adding its entry to `src/package-lock.json` in the same change.

## What the second designer adds

The second designer is the Hierarchical Requirement Designer, in [`src/designers/hierarchical-requirement`](../src/designers/hierarchical-requirement), the first of DESL's `hierarchy` surface kind. Its document is a Markdown file that an agent can write too, so it differs from the Knowledge designer where a document of that kind must:

- **Recognised by its envelope.** [`Designer.cs`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Designer.cs) carries a `DesignerClaim` on `.md` whose envelope is the binding's first line, `<!-- ded: 0.2 designer: etalii/hierarchical-requirement -->`, so an ordinary Markdown file stays the Markdown editor's and a document needs no registration to open. The registration is created beside the body with the first setting the person changes, a fold, and holds only what the Markdown does not: the option lists' colours, the folds and the saved filters.
- **A page, not a table.** [`HierarchicalRequirementSession`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/HierarchicalRequirementSession.cs) reads the body and its registration through the binding, watches both, and sends the whole page through [`HierarchicalRequirementSurfaceMapper`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/HierarchicalRequirementSurfaceMapper.cs), which names an entry by its number when that is usable and by `line/<n>` otherwise. A gesture names an operation of the specification, and [`HierarchicalRequirementGestures`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/HierarchicalRequirementGestures.cs) is the table that plans each one; an operation not built yet is refused with the reason. A fold is written to the registration's `collapsed` block, which the binding declares outside the history, so it is no undo step.
- **An edit is a command, and every edit numbers.** `setTitle` and `setDescription` ([`TextOperations`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Operations/TextOperations.cs)) run through the project's history as a [`HierarchicalRequirementEditCommand`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Commands/HierarchicalRequirementEditCommand.cs) carrying the bytes the gesture was made against: a file that differs from them is refused with the sentence that it changed while being edited, and nothing is written. [`BodyEdit`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Operations/BodyEdit.cs) makes every edit write the numbers reading gave each placeholder and the counters' marks besides itself, planned through the FBL library as one edit. The inverse, [`RestoreRequirementFilesCommand`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Commands/RestoreRequirementFilesCommand.cs), answers `CommandResult.Outdated` when another program changed the file since, as Knowledge's restore does.
- **Two writers.** The module's store, [`IHierarchicalRequirementDocumentStore`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/IHierarchicalRequirementDocumentStore.cs), is told before a command writes, so the session labels what the watcher then hears as its own edit rather than a change from outside. A change from outside is read again and sent whole, with its cause; a read that finds the file half-written is tried again, and a file that cannot be read keeps the last page, read-only, with the reason. On the client, a title or description is typed in place, and a change from outside while a field is open shows the bar of [`ConflictBar`](../src/client/src/hierarchySurface/library/ConflictBar.tsx), which drops the text or keeps it for a new edit of the file as it now is.
- **Shaping the hierarchy.** The adds, the moves and the delete ([`StructureOperations`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Operations/StructureOperations.cs)) go through the same command, which carries the gesture's params, so a move names the item it goes into and the sibling it goes after. The numbering is written first and the structure planned against the bytes it leaves, so a move or a delete of an entry that holds a placeholder does not plan two overlapping changes; one undo takes back both. A new document is the binding's template, written by `TemplateWriter.Produce` from [`HierarchicalRequirementDocumentTemplate`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/HierarchicalRequirementDocumentTemplate.cs), with no registration. Ctrl+Enter and Ctrl+Shift+Enter are context actions of an entry in the `DiagramElement` scope ([`HierarchicalRequirementContextActionProvider`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/HierarchicalRequirementContextActionProvider.cs)); the page sends a chord of a key its definition lists under `shortcutKeys` to the backend, which decides what it runs. On the client, the add controls, the drag by a box's grip and the delete's question are in [`editing/`](../src/client/src/hierarchySurface/library/editing), and the page opens the title of a node an add brought for typing.
- **Assessments.** The four assessment operations ([`AssessmentOperations`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Operations/AssessmentOperations.cs)) go through the same command. An add names the entry, the others the assessment by its id in the model the page was sent, so the session checks the target among the notes rather than the nodes. The library writes the stored form of a kind and needs `resolved` on an add, or the checkbox comes out empty. On the client, the icon at a box's top right and the list it opens are in [`notes/`](../src/client/src/hierarchySurface/library/notes); which operation each of the list's gestures sends, their params and the list's words are the definition's `notes`.
- **References.** A reference is text: the specification's `mentions` pattern finds it in a description or an assessment, the model carries each one's offset and the node it names (empty when it names none, which `std.mentions` reports), and nothing in the backend is particular to it. On the client, [`references/`](../src/client/src/hierarchySurface/library/references) holds the lookup `#` opens in a description field, the box a reference stands as, and `reveal.ts`, which works out the focus and the expands that show a reference's target; expanding is the page's own collapse, so following a reference writes only the registration.
- **Tags, in both files.** The tags an entry carries are in the Markdown file; the tag list's colours and order are the registration's `tags` block, which the binding keeps in the history. The six tag operations ([`TagOperations`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Operations/TagOperations.cs)) go through the same command, which then writes the body, the registration or both as one step, and its inverse puts back every file it wrote. A registration the body has none of is created as the step's starting point, outside the step, and the first change of a list its block does not hold writes the whole list, its implicit members first ([`RegistrationEdit`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement/Operations/RegistrationEdit.cs)). An edit of the registration alone writes nothing to the body, so it numbers no placeholder. On the client, [`labels/TagField.tsx`](../src/client/src/hierarchySurface/library/labels/TagField.tsx) is the field below the title, on the shared `SearchList`, and edits the list in the table's own `OptionsEditor`; a label the definition gives an `edit` is drawn as that field.
- **Its client** is the same three files: [`hierarchicalRequirementDefinition.ts`](../src/designers/hierarchical-requirement/client/hierarchicalRequirementDefinition.ts), the levels' and entries' types, the labels with their prefixes, each assessment kind's icon and the icon for several, which operation each gesture sends with the add controls' labels, the move's params, the delete's question, the assessments' operations and words and the tag field's operations, which `register.test.ts` holds to `hierarchical-requirement.des`; [`HierarchicalRequirementPanel.tsx`](../src/designers/hierarchical-requirement/client/HierarchicalRequirementPanel.tsx), `useHierarchySurfaceStream(path)` handed to `HierarchySurface`; and [`register.ts`](../src/designers/hierarchical-requirement/client/register.ts).

[`HierarchySurfaceFlow.Tests`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement.Tests/HierarchySurfaceFlow.Tests.cs) goes through the host with the module deployed: each Markdown file opens in the tool it is for, the page arrives whole and opening it writes nothing, and a fold is written and is no undo step. [`RegistrationDeleted.Tests`](../src/designers/hierarchical-requirement/backend/EtAlii.Adp.Designer.HierarchicalRequirement.Tests/RegistrationDeleted.Tests.cs) deletes the registration under an open page and creates it again: nothing an agent reads is lost.


What a designer needs beyond the scan is decided by its specification, the way `modular-text-editors` decided the editor family's: the routing and session seams the host serves designers through (the definition and its catalog are in place), and - when ADP specifies designer types in a language - DESL, the Designer Specification Language, with the designs users create stored as DED, the Designer Definition Language.
